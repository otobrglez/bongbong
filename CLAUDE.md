# bongbong

Bongbong is a tank shooter game. Main purpose of this game is to be a fun, fast and entertaining game where player shoots other tanks. Artisticly the game trys to be "pixelated" and it tries to mimic old tank arcade games. The twist of this game is to have semi-realistic physics, intersting and challenging AI and ability to build your own battlefields.

# Architecture & Development

- This application is written in Rust.
- The main library it uses is Raylib (written in C) but not directly it uses sola-raylib wrapper/bindings designed to work well with Rust. Source code for raylib in C is available at `../raylib`.
- Game uses sola-raylib bindings for Raylib. Source code for sola-raylib is available at `../sola-raylib`. When needed you can always consult this source code and its wide collection of examples.
- The game uses rapier physics game engine written in Rust. The source code for engine is available at `../rapier`. When working on physics consider consolidating the source code.
- Dependencies and environment is isolated with the help of devenv (Nix) so there is `devenv.nix` and `.envrc` that has some credentials and it defines Rust versions etc.
- For faster development loop developer runs `cargo watch -x "run"` that watches for source changes, compiles project and boots the application. This gives developer better overview.


# Game structure
- Main entrypoint is `src/main.rs`
- Assets, sprites, shaders etc live inside `static/`
- Tools / scripts and other things needed for the development live inside `tools/`

## Module map
- `main.rs` — entrypoint: window/texture/shader setup, owns the raylib handle and the main loop. Gathers each frame's raw input into a `simulation::Input` and passes it to `Game::update` — nothing past this file ever touches `RaylibHandle` for input.
- `lib.rs` — shared *layout* constants and types (`Position`, sprite-atlas columns/sizes, `*_VARIANTS`, collider bounding boxes, grid/physics sizes). Heavily commented inline — treat those comments as the source of truth over restating them elsewhere. **Gameplay/feel knobs no longer live here**: everything that's a design decision rather than an asset description (speeds, forces, damage, fire intervals, AI ranges, cosmetics, shader FX) moved to `tuning.rs`'s table in 2026-09 — don't add a new `pub const` knob here, add a row there.
- `tuning.rs` — the runtime-tunable knob table (docs/runtime-tuning-design.md): one `tunables! { group x { /// doc  name: ty = default in min ..= max [labels NAMES] [@ Live|Spawn|Restart]; } }` row per knob (~185 rows in 15 groups), expanded by a `macro_rules!` into the `Tuning` struct, `Tuning::DEFAULT`, the static `Tuning::SCHEMA` (name/group/type/doc/range/labels/applies - the doc comment is *captured*, so it's what the dev panel shows), and range-checked `get`/`set` by name (`name`, or `name.label`/`name.<i>` for an array row like `wall_max_health: [f32; 4] labels MATERIAL_NAMES` / the `[f32; 12] labels TANK_NAMES` per-chassis tables, indexed by `material as usize`/`tank.row`). Read everywhere via `tuning().field` (a global `RwLock` read guard - bind once in hot loops). **Writes only at the frame boundary**: transports stage a patch (`submit_json`/`submit_reset`, or `submit_file` for `--tuning <file>`) and `main.rs` calls `apply_pending()` right before `Game::update`, so a frame never sees two values of one knob and nothing in `simulation/` ever mutates tuning; `request_restart`/`take_restart_request` is how the panel's Restart button becomes an `Input::restart_pressed`. Derived values (`engage_ring_radius()`, `enemy_retreat_range()`, `minigun_burst_cooldown_seconds()`) are methods, not rows, so they track their base knob. `Tank::speed` became `Tank::speed_scale` (a per-tank factor) so `tank_speed`/`enemy_speed` are live mid-round; `RippleFx::set_tuning` re-uploads the shader uniforms when the table changes. Unit tests (`cargo test --lib tuning`) cover the macro, JSON patch/diff round-trip, and "Copy as Rust" output; they work on local `Tuning` values only - never mutate the global in a test, the suite runs in parallel threads.
- `capi.rs` *(feature = "dev-tools", dev/QA-only)* — the `extern "C"` surface over `tuning.rs` (`bb_tuning_schema_json`/`_current_json`/`_diff_json`/`_diff_rust`/`_apply_json`/`_reset`, `bb_game_restart`, `bb_last_error`) that the web page's tuning panel calls through `Module.ccall`. Returned strings live in a thread-local scratch buffer valid until the next `bb_*` call. `main.rs` calls `capi::keep_alive()` so the functions are actually referenced from the binary, and `build.rs` emits `-sEXPORTED_FUNCTIONS=_main,_bb_...` for the `bongbong` bin only, only on `wasm32-unknown-emscripten` with the feature on (`capi::EXPORTS` and the `build.rs` list are checked against each other by a unit test).
- `simulation/` — the simulation layer, a directory module (`crate::simulation` paths are unchanged). `mod.rs` owns `Game` (state, `Game::init`, and `Game::update` as a sequence of named phase methods - timers, frog, pickups, player, enemies, lasers, `step_world`, ram, shell-vs-shell, projectile hits, explosions, cleanup, round end - sharing a per-frame `Frame` context that carries the round RNG, the terrain snapshot and everything spawned/applied only once no query is active). `weapons.rs` fires shots and ticks queued twin-barrel/burst shots (`dispatch_fire`/`tick_queued_shots`, shared verbatim by player and AI) and defines the `Projectile` trait that lets one hit loop serve shells, bullets and plasma. `hits.rs` is the **only** projectile hit test: `Terrain` (a per-frame snapshot of seam-closed obstacle boxes, frog and walls) plus `Terrain::sweep`, a nearest-entry-time segment-vs-box sweep over each projectile's whole movement this frame - projectiles have no physics body and rapier is not consulted for hits; `Terrain::line_of_sight` is the AI's fire gate. `combat.rs` applies a resolved hit (`Game::apply_hit`: damage, knockback, frog hop, `Ai::notify_hit`), `ram` (wrecks neither deal nor take ram damage) and explosions. `engage.rs` is the engagement-slot ring (`EngageRing`, unit-tested with closures; reachability comes from one `Grid::components` flood fill per frame, not per-candidate A*). No `RaylibHandle`/drawing dependency by design — driving a round forward needs nothing but this module and a `simulation::Input`. Projectiles are integrated inside the fixed-step loop with the physics step, and on the end screen they still fly and land (without damage) while the restart counts down.
- `battlefield.rs` — static terrain *placement* for a fresh round: boundary walls (`spawn_walls`) and the loaded `map::MapFile`'s walls/road/frog/pickup-slots (`spawn_from_map`), plus enemy placement: `sample_clear_position` (bounded rejection sampling, `None` on the attempt cap - callers then snap a sample to `Grid::nearest_open`, never use a rejected sample), `enemy_spawn_legal` (the one spawn-legality predicate, shared with `maplint.rs`'s spawn-band capacity count: border band + player clearance + a `Grid::usable` nav cell + a worst-case tank box clear of every wall tile - there is no separate `OBSTACLE_CLEAR`-style distance term any more, it made the default map's band unsatisfiable), `relocate_unusable_spawns` (post-layout audit that moves any enemy whose cell is blocked or boxed in) and `max_tank_avoidance_radius` (the clearance margin obstacle placement, spawn legality and the per-frame pathfind grid all use). `simulation/mod.rs`'s `spawn_tests` lock in that no enemy starts overlapping a wall on the default map. There is **no procedural fallback battlefield any more** — a map (`-m`/`--map`, or `maps/default.toml` when none is given, see `main.rs`) is the only source of static terrain; the old random "HELLO"-fortress/scattered-obstacle-structures generator was removed outright, not just made optional. The obstacle *entity type* (`Obstacle`) and the decorative ground layer (`ground.rs`) stay in their own modules; this one only decides where things go.
- `map.rs` — the on-disk battlefield map format (`MapFile`/`CellObject`, TOML under `maps/`) and the grid↔world coordinate conversion (`cell_to_world`/`world_to_cell`) both `battlefield.rs` and `editor.rs` share. A map only encodes *interior* terrain (walls, road, one frog, health/ammo pickup slots) — border walls and enemy/player spawns stay procedural on top of it. See docs/map-editor-design.md.
- `editor.rs` *(feature = "map-editor", dev-only, never in a release build)* — the in-game battlefield map editor (`MapEditor`): click-to-place/erase palette (walls/road/frog/pickups/eraser), Save/Load/New/Close toolbar, panel chrome. Launched via `cargo run --features map-editor -- --editor [--map <file>]`. See docs/map-editor-design.md.
- `game.rs` — the presentation layer: `Game::render` plus `Textures`/`Effects`. Reads `Game`'s state (owned by `simulation/`) and draws it; never mutates it.
- `tank.rs` — tank entity: state, movement, drawing.
- `shell.rs` — projectile entity: state, movement, drawing. See docs/SHELLS_SPEC.md for the `shells.png` row/column layout and the per-tank variant tables in `lib.rs`. Also home to `Owner` (who fired something — shared by `Shell`, `bullet::Bullet`, plasma and the laser; `Tank::owner()`/`Owner::slot()` convert to and from `Tank::owner_slot`, and `Owner::same_side` is the friendly-fire test).
- `laser.rs` — the laser weapon's on-screen flash (`LaserBeam`/`LaserVariant`): a limited-charge, instant-hit weapon granted by `pickup::PickupKind::Laser`, resolved same-frame by `Game::resolve_lasers` (no travel time, no sprite — just a drawn line, unlike `Shell`/`Bullet`).
- `bullet.rs` — the minigun's individually-simulated projectile (`Bullet`/`BulletState`): mirrors `shell.rs`'s shape (position/velocity/state) but with a compact 3-state machine (Muzzle/Flying/Hit) instead of `Shell`'s 7, since a burst fires them far too rapidly in succession for an elaborate wind-up/impact sequence to read well. See docs/BULLETS_SPEC.md for the `minigun_bullets.png` layout.
- `plasma.rs` — the plasma cannon's projectile (`Plasma`/`PlasmaState`): a limited-ammo weapon granted by `pickup::PickupKind::Plasma` (`Tank::plasma_ammo`), fired the exact same way a shell is — straight down the barrel, a twin-barrel chassis firing one bolt per barrel a beat apart (`Tank::pending_plasma_shot` mirrors `Shell`'s `PendingShot`) — and sharing `ShellState`'s overall Fire/Flying/Hit choreography/timings (`Flying` alone spans a 4-frame baked breathing cycle, not one static frame — see `flying_col`), but dealing `PLASMA_DAMAGE_FACTOR` (24%) more damage and rendered as a glowing, pulsating orb (`draw_plasma`'s runtime sine-wave glow layered on top of the baked `static/plasma.png` sprite — see docs/PLASMA_SPEC.md) that bursts into a small electric/sci-fi splash on impact instead of a shell's smoke-and-fire blast. Comes in two `PlasmaVariant`s (Teal base, Purple rarer/harder-hitting — `PLASMA_PURPLE_PICKUP_CHANCE`/`PLASMA_PURPLE_DAMAGE_FACTOR`, same reroll-on-pickup mechanism as `laser::LaserVariant`), each its own baked sheet row (a runtime tint was tried and rejected — see docs/PLASMA_SPEC.md §4). Unlike `shell.rs`, that row is keyed by ammo variant, not shooter chassis (`bullet.rs`'s "shared art" convention), and a bolt never ricochets.
- `pickup.rs` — battlefield pickups (`Pickup`/`PickupKind`: Health, Ammo, Laser, Minigun, Plasma, SpeedUp, Shield): position + kind, no physics body, collected by pure proximity (see `simulation/mod.rs`'s pickup phase). Placed via fixed map slots (`map.rs`'s `CellObject::Pickup`), not randomly. `SpeedUp` is a timed stat buff rather than a weapon/ammo grant: it sets (not adds to) `Tank::speed_boost_timer` to `SPEED_BOOST_DURATION_SECONDS`, during which `Tank::effective_speed` is scaled by `SPEED_BOOST_MULTIPLIER` — collecting another one while already boosted refreshes the timer instead of stacking, so a tank is only ever under one speed boost at a time. `Shield` (the rainbow shield) is the same shape of timed buff: full heal (`Tank::damage = 0`) plus `Tank::shield_timer` set to `shield_duration_seconds`, during which `Tank::take_damage` — the **only** path that adds damage to a tank (shells, ram, explosions, frog bite all go through it) — is a no-op; hit flash/knockback/AI alert still fire so a blocked shot visibly lands. Drawn as a hue-cycling ring under the hull (`tank::draw_tank_shield`). It is the one pickup that is normally *not* slot-backed: `maybe_spawn_bonus_shield` rolls `shield_near_health_chance` every time a Health slot is spawned or respawned and drops a shield in a free neighbouring cell (`bonus_shield_cell`), so the respawn timer's "field is full" test counts only slot-backed pickups (`slot_backed_count`). Any tank, player included, also starts shielded with `spawn_shield_chance` odds (rolled in `Game::init`).
- `obstacle.rs` — static battlefield terrain: walls built from one of four materials (`Material`: Brick, Iron, Wood, Glass), each with its own decay/rust/burn lifecycle — state and drawing. See docs/WALLS_SPEC.md for the `walls_sheet.png` layout.
- `ground.rs` — the decorative grass/dirt/road floor layer, built once per round by `Game::init` and drawn first in `render`, before everything else. No physics, no gameplay effect. Sourced from the third-party Puny World tileset (`static/punyworld/` - see docs/GROUND_SPEC.md and static/punyworld/SOURCE.md) using that pack's own pre-built Tiled autotile data rather than a hand-rolled one. This tileset's own colours are also the source of `tools/punypalette.py`, the shared palette every other generated sheet now draws from - see the Asset pipeline section below.
- `physics.rs` — rapier2d wrapper (`Physics`): solid bodies only (tank movement colliders, walls, obstacles, the frog), impulses, contact read-back, the fixed-timestep step. No sensors or collision groups any more - projectile hits are pure geometry in `simulation/hits.rs`. See docs/physics-engine-design.md ("Projectile hit testing").
- `track.rs` — tank tread marks left on the ground.
- `damage_stage.rs` — escalating damage overlay drawn on top of a tank.
- `ai.rs` — enemy decision-making (`Intent`, targeting, firing); builds and ticks behavior trees from `bt.rs`. `Ai::steer` routes its naive straight-line heading through `pathfind::Grid` before applying direction commitment/predictive-dodge, so obstacles are just another reason the heading bends. Two safety nets on top of that routing, both added after denser obstacle layouts started producing stuck tanks: (1) an obstacle-ahead override in `steer` bypasses the normal `AI_DIR_HOLD_SECONDS`/`AI_DIR_SWITCH_MARGIN_PX` commitment gate (debounced by the much shorter `AI_OBSTACLE_OVERRIDE_HOLD_SECONDS`, so it doesn't itself reintroduce jitter) whenever the committed heading is about to walk into a grid cell `pathfind::Grid::blocked_ahead` already knows is blocked; (2) a stuck-escape (`Ai`'s `was_moving`/`stuck_timer` fields, `STUCK_SPEED_EPS`/`STUCK_ESCAPE_SECONDS`) catches everything (1) can't, including a genuine no-path layout - `simulation.rs` reads each enemy's *real* physics velocity (`Physics::velocity`, not the commanded `Tank::velocity`) each frame and passes it into `Ai::think` as `real_velocity`, purely as a plain vector (never `Physics` itself - `Ai` stays snapshot-only per the AI-decoupling principle below); `think` projects it onto the heading it commanded last tick, so it can tell "commanded to move" apart from "actually got somewhere that way" - a tank carried sideways by a jam of other tanks counts as stuck even at full speed (`ai.rs`'s `stuck_tests`).
- `bt.rs` — small generic, game-agnostic behavior-tree engine (Selector/Sequence/Condition/Action) used by `ai.rs`.
- `pathfind.rs` — small grid-based A* (`Grid`) so AI routes around static obstacles; game-agnostic like `bt.rs`. Rebuilt fresh each frame in `simulation.rs` from the current obstacle layout, per the AI-decoupling principle in docs/physics-engine-design.md (AI reasons over snapshots, never the ECS/physics world directly). Has its own `#[cfg(test)]` unit tests (the one algorithmic, non-visual piece of the codebase) — run with `cargo test --lib pathfind`.
- `shockwave.rs` — `RippleFx`/`RippleTuning`: post-processing ripple-shader effect driver for the GLSL shaders in `static/*.fs` (shockwave, muzzle flash, impact).

## Asset pipeline (generated, not hand-drawn)
- The three sheets `main.rs` actually loads for tanks/shells/walls — `static/scifi_tanks_sheet.png`, `static/shells.png` (18 variants), `static/walls_sheet.png` — are all procedurally generated by the Pillow-based scripts in `tools/spritegen/` (`gen_tanks.py`, `gen_shells.py`, `gen_walls.py`; one file per sheet, deterministic fixed seeds). Regenerate in place with e.g. `SPRITE_OUT=static python3 tools/spritegen/gen_tanks.py` — default `SPRITE_OUT` is `assets/sprites`, so the env var is required to write into `static/` where the game reads from (it also writes ~150 individual per-tank debug PNGs alongside the sheet - `main.rs` never loads these, only the combined sheet, so delete them after regenerating rather than leaving them in `static/`). Requires Pillow, not currently declared in `devenv.nix`. **Plain `pip3 install pillow` / `python3 -m pip install pillow` do NOT work here** - the nix-provided `python3` has no `pip` module at all (nix expects packages added via nix, not pip) - use `nix-shell -p "python3.withPackages (ps: [ps.pillow])" --run "SPRITE_OUT=static python3 tools/spritegen/gen_tanks.py"` instead (or add `pillow` to `devenv.nix`'s `languages.python`/`pkgs.python3.withPackages` for a persistent fix).
  Specs, one per sheet: `docs/SPRITESHEET_SPEC.md` (tanks), `docs/SHELLS_SPEC.md` (shells), `docs/WALLS_SPEC.md` (walls), `docs/BULLETS_SPEC.md` (minigun bullets), `docs/PLASMA_SPEC.md` (plasma bolts) — all self-contained (column/row maps, pivots, palettes), no need to open the PNGs to slice or edit them correctly.
- The minigun's two Pillow-generated assets follow the exact same `tools/spritegen/` convention as tanks/shells/walls: `tools/spritegen/gen_bullets.py` → `static/minigun_bullets.png` (the bullet sheet, see docs/BULLETS_SPEC.md) and `tools/spritegen/gen_minigun_mount.py` → `static/minigun_mount.png` (a 3-frame turret-mounted barrel-cluster overlay drawn by `tank::draw_minigun_mount`, one "hot barrel" per frame, cycled while firing rather than rotated — this is a top-down game, so a barrel cluster's real rotation axis points along the ground plane, edge-on to the camera, and spinning the sprite in the screen plane would read as a helicopter rotor seen from above; see docs/SPRITESHEET_SPEC.md's composition-order section and the generator script's own doc comment).
- The plasma cannon's two generated assets follow the same conventions already established above: `tools/spritegen/gen_plasma.py` → `static/plasma.png` (the 7-column bolt/burst sheet, Pillow-based like `gen_shells.py`/`gen_bullets.py` — see docs/PLASMA_SPEC.md) and `tools/gen_plasma_pickup.py` → `static/pickups/plasma.png` (the ground pickup icon, raw PNG bytes, no Pillow — same convention as `gen_laser_pickup.py`/`gen_minigun_pickup.py` below).
- **Every generated sheet's colours come from one shared palette** (`tools/punypalette.py`, a curated set sampled directly from the third-party Puny World ground-layer tileset) — see `docs/PALETTE.md` for the why/how, the pixel-level verification method, and why this replaced an earlier pass built on the generic Resurrect 64 palette (`tools/resurrect64.py`, kept only as historical reference - nothing imports it anymore). All generators (`gen_tanks.py`, `gen_shells.py`, `gen_walls.py`, `gen_damage.py`, `gen_bullets.py`, `gen_minigun_mount.py`, `gen_plasma.py`) import `punypalette`; any new sprite work should too rather than introducing a fresh literal colour.
- **Pickup icons (`static/pickups/*.png`) are a separate, smaller pipeline from the sheets above** — one standalone 32x32 PNG per kind, deliberately *not* palette-snapped (loud/high-contrast, so a pickup reads at a glance against muted terrain - see `static/pickups/SOURCE.md`). `health.png`/`ammo.png` are copied unmodified from a third-party pack; `laser.png`/`minigun.png`/`plasma.png`/`speedup.png` are generated from scratch by `tools/gen_laser_pickup.py`/`tools/gen_minigun_pickup.py`/`tools/gen_plasma_pickup.py`/`tools/gen_speedup_pickup.py` (and `shield.png` by `tools/gen_shield_pickup.py`, which instead reads `health.png` and sweeps its red through the rainbow so the shield reads as a rainbow health pack), which write raw PNG bytes directly (no Pillow), same convention as `tools/gen_damage.py`.
- `static/damage.png` is generated by `tools/gen_damage.py`, which writes PNG bytes directly (no Pillow dependency). `static/tracks.png` is a small hand-authored/static asset with no generator script — its one dark-earth tone was recolored onto the palette with a one-off pixel remap rather than a persisted tool, since there's nothing else to regenerate.
- **`tools/gen_shells.py` (the old, no-Pillow, hand-rolled-PNG-writer script) is stale** — it still emits a 3-variant, 224×96 `shells.png`, superseded by `tools/spritegen/gen_shells.py`'s 18-variant, 224×576 sheet that's actually in `static/` and wired up (`SHELL_VARIANTS = 18` in `lib.rs`). Do not run the old script — it would regress the live sheet back to 3 variants. Kept around only as the generator for reference/history; not part of the live pipeline.
- `static/tanks.png`, `static/tanks_turret.png`, `static/tanks_candy.png` (an earlier tank-art iteration `main.rs` no longer loads, plus a recolor preview generated from it) and `static/walls_sheet_light.png` (an unreferenced walls-sheet variant, never wired into `main.rs`) were deleted as unused - confirmed via `main.rs`'s five `load_texture` calls (`scifi_tanks_sheet.png`/`shells.png`/`damage.png`/`tracks.png`/`walls_sheet.png`, all literal paths, nothing dynamic) being the only textures the game ever loads. `tools/analyze_turrets.py` and `tools/gen_tanks_candy.py` read the now-deleted `static/tanks.png` and will error if run - left in place as historical reference (same convention as the stale `tools/gen_shells.py` above) rather than deleted, since removing tools wasn't asked for.
- To change a live sprite, edit the relevant `tools/spritegen/*.py` (or `gen_damage.py`) generator and rerun it — don't hand-edit the PNGs.
- **`walls_sheet.png` is chunky-pixelated to match tanks' look, without changing its dimensions.** Tanks draw their 32×32 source tile at `Tank::scale = 2.0` (`tank.rs`), so each source pixel covers a 2×2 on-screen block; obstacles draw their own 32×32 tile at `OBSTACLE_SCALE = 1.0` (`lib.rs`), 1:1, which used to read as crisper/finer than tanks despite identical source resolution — not more detailed, just unstretched. Bumping `OBSTACLE_SCALE` itself isn't viable (it would double obstacles' on-screen size and break `OBSTACLE_GRID_SIZE`/pathfinding-cell/collider alignment, which all assume `Obstacle::size() == OBSTACLE_TEXTURE_SIZE`), so instead `gen_walls.py` bakes the same 2× chunkiness into the art: a `pixelate()` post-process (NEAREST downsample-then-upsample, never box/average — averaging would blend adjacent pixels into new off-palette colours) runs once on the finished sheet right before it's saved, so none of the brick/iron/wood/glass decay-stage drawing logic needed to change. `PIXELATE_FACTOR = 2` deliberately matches `Tank::scale` exactly. Sheet dimensions, tile size, and column/row layout are all unchanged — only pixel content inside each tile changed, verified by direct crop/magnify comparison against the pre-change sheet (backed up in `static/_backup/wall-pixelate-*/`).
- Before a sweeping recolor/art pass, back up the current sheets and the generator source that produced them into `static/_backup/<label>-<timestamp>/` and `tools/spritegen/_backup/<label>-<timestamp>/` (plain file copies, not tracked specially) so the previous look stays around to compare against or revert to. See `docs/PALETTE.md` for every past pass's backups (pre-Resurrect64 originals, two R64 sub-passes, now Puny Palette) as an example of the convention.
- **The ground/terrain layer (grass/dirt/road) is the one exception to "generated, not hand-drawn."** `static/punyworld/punyworld-overworld-tileset.png` is third-party art (see `static/punyworld/SOURCE.md`), not a `tools/spritegen/` output. Everything *else* was recolored to match *it* (`tools/punypalette.py` - see `docs/PALETTE.md`), not the other way around: once the ground layer actually shipped, the tanks/walls/shells' previous Resurrect-64-vivid colours read as neon plastic next to Puny World's much softer terrain. `ground.rs` builds the per-round layout and draws it; full design + the Wang autotile tables it uses (extracted from the pack's own Tiled `.tsx`) are in `docs/GROUND_SPEC.md`. An earlier from-scratch procedural version (`tools/spritegen/gen_ground.py`) was superseded before ever being wired in - kept only as historical reference, not part of the live pipeline.
  - **The live tileset PNG is a retinted copy, not the pristine pack art.** The pack's own grass is yellow-green and its dirt paths bright yellow-khaki, which made the whole battlefield read yellow/green (user feedback, 2026-08). `tools/retint_ground.py` applies a smooth hue-based HSV curve (grass hue-shifted toward the pack's own deeper tree-green, dirt muted toward earth-tan; wood/red/teal/water untouched) — it always reads the pristine original kept at `static/punyworld/_original/punyworld-overworld-tileset.png` and writes the live path, so it's idempotent; tweak its `CURVE` control points and rerun to iterate. Never edit the live PNG directly, and never overwrite `_original/`. Relatedly, `battlefield.rs`'s `FORTRESS_ROAD_SURROUND` is now 0 (was 1): the dirt ring around the "BONG!" glyphs visually merged into one giant khaki moat — see that constant's doc comment.

## Conventions
- **Comments describe the code as it is now, not its history.** Say what a thing does and why the rule exists; leave "used to", "before X existed", which probe sweep found what, and cross-references to deleted code out - git and `docs/` hold the history. A doc comment that narrates past versions is the main way this codebase's comments drifted from its code (a 2026-09 review of `simulation.rs` found a third of the file was comments, several describing behaviour that no longer existed). Also: consecutive `///` lines merge into one doc, so a blank line must separate one item's doc from the next item's.
- Tank/shell rotation `0.0` = facing up.
- **A new gameplay/feel number is a `tunables!` row in `tuning.rs`, not a `pub const` in `lib.rs`** (which is layout only now - see the module map). Read it via `tuning().name`; never write the global outside `tuning.rs`'s staging path; never `const X = tuning().y` (not const-evaluable - make it a fn) and never recover a direction by dividing by a speed knob that may have changed since the projectile spawned.
- Movement is 4-direction, constant-speed, no momentum: pressing a direction snaps the hull to face it and moves at a fixed speed; releasing stops instantly.
- Sprite-sheet layouts, damage-stage frame groupings, and speed/damage tuning curves are documented as comments in `lib.rs` next to their constants — check there first.
- **Seeded-replay determinism on the simulation path** (docs/gameplay-verification-design.md): all round randomness flows from `Game`'s one seeded `SmallRng` stream — never call `rand::rng()` on the simulation path (the only allowed uses are the *seed draws themselves* — `Game::init`'s entropy fallback and the probe's base-seed draw — plus the editor's cosmetic `ground_seed`), and never iterate a `HashMap`/`HashSet` where the loop body consumes RNG, spawns entities, or breaks ties — sort first (see `MapFile::iter_cells`, which sorts for exactly this reason). `simulation/mod.rs`'s `determinism_tests` catches violations.
- `shells.png` has row-variants (`SHELL_VARIANTS`), matched to chassis via `TANK_SHELL_VARIANT_BY_ROW`/`TANK_SHELL_VARIANT_STAGGERED_BY_ROW` (barrel count, size class, accent colour) rather than rolled randomly. `Tank::shell_variant` is set at spawn and re-set on every shot the tank fires, alternating between the two tables via `Tank::alternate_shot` — a no-op for single-barrel chassis, whose two table entries are identical. The flying frame (col 3) is pixel-identical across all rows by design — only the fire/hit frames differ — so a shell looks the same in flight no matter which tank fired it.

## Testing & tooling
- No project-wide automated test suite — verify changes by running the game (`cargo run` or `cargo watch -x "run"`) rather than assuming test coverage. The exceptions live in `cargo test --lib`: `tuning.rs`'s tests (the knob table/JSON contract) and `capi.rs`'s (with `--features dev-tools`), `pathfind.rs`'s tests (A* + `path_cost` + `component_tests` for the flood-fill reachability), `simulation/hits.rs`'s `shell_sweep_tests` (segment-vs-AABB geometry, reflect axis), `simulation/combat.rs`'s `ram_tests`, `simulation/engage.rs`'s slot-assignment tests, `simulation/mod.rs`'s `mechanics_tests` (headless scenario tests on tiny inline maps: pickup respawn delay, twin-barrel ammo cost, edge-triggered shell fire - add one whenever a comment promises a mechanic), `battlefield.rs`'s `tile_seam_tests`, `tank.rs`'s `weapon_queue_tests`, `ai.rs`'s `stuck_tests` (progress-along-heading stuck detection and its escape), `maplint.rs`'s `map_lint_tests` (the static battlefield-map linter — see its own bullet below), and `simulation/mod.rs`'s `determinism_tests` (the seeded-replay guard — see the probe bullet below). Everything else stays play-tested only.
- No `rustfmt.toml` or clippy config is checked in; there's no enforced formatting/lint convention yet.
- **Native runtime tuning**: `cargo run -- --tuning knobs.json` loads a JSON patch (`{"tank_speed": 300, "wall_max_health.wood": 50}` - the panel's "Copy JSON" output) at startup and re-applies it whenever the file's mtime changes (polled every 30 frames), so any editor is a live tuning UI on native; a bad file fails fast at startup, a bad edit later is reported on stderr and ignored. The probe takes the same `--tuning` flag (applied once, echoed as `tuning=` in its header and as a `"tuning"` object in every `--json-out` record), so `(seed, tuning diff)` is the replay pair for a tuned sweep. `cargo run --bin probe -- --tuning qa.json --print-rust` renders that JSON as `tunables!` rows to paste over the matching rows in `tuning.rs` when a QA'd set should become the default (the web panel's "Copy as Rust" button does the same from the browser).
- **`src/bin/probe.rs` — headless gameplay/mechanics probe.** Drives `simulation::Game` frame-by-frame with a scripted `Input` sequence and no window/renderer, then dumps tank state (position, velocity, rotation, damage, ammo, wreck) as text. Use this as the default way to verify or explore gameplay mechanics — movement, damage exchange, AI behavior, round outcome — since it's fast (no GPU/window) and its output can be read directly instead of eyeballing screenshots. Run with `cargo run --bin probe -- --scenario <afk|advance|brake|circle> [--enemies N] [--frames N] [--log-every N] [--seed S] [-m <map.toml>] [--json-out F] [--budget kind=N ...] [--heatmap]`; `--help` lists current options and each scenario's own doc comment. `-m`/`--map` picks the battlefield (same semantics as the game binary; default: the embedded `maps/default.toml`, so a bare probe run exercises the battlefield the game actually ships with — there's no more random/dense-obstacle stress-test flag, `--obstacles` went with the procedural generator; see `battlefield.rs`'s module map entry). **`maps/test/` is an adversarial fixture corpus** for exactly this flag — six hand-built layouts, one per known stuck/scrape failure class (u-trap, choke, tight-corridors, frog-block, maze, pockets), each with an explicit `Start`+`Frog` cell and a `tanks` count so runs are comparable; per-fixture intent, design constraints (the k≥6 corridor-clearance rule, spawn-band envelope, keep a route outside `BORDER_MARGIN`) and seeded baselines live in docs/gameplay-verification-design.md §2.2 and each file's own header comments (which an editor re-save would drop — edit fixtures by hand). Built on `Game::outcome()`/`Game::tank_snapshots()` (simulation.rs), the small public read-only accessors added alongside the probe for exactly this purpose — extend those, not raw `world`/`Entity` access, if a scenario needs more state (a probe binary is a separate crate from the library, so it only sees `pub` API, not `simulation.rs`'s `pub(crate)` internals). Add new scenarios by extending the `Scenario` enum and `input_for_frame` in `probe.rs`.
  - Limitation: covers logic only (movement/damage/AI/outcome), not rendering, shader effects, or "feel" — for that, use the `run` skill against the real windowed game.
  - **Fully reproducible given a seed** (Phase 1 of docs/gameplay-verification-design.md): a round's entire RNG lives in one `SmallRng` stream seeded in `Game::init` (`Game::seed_override`/`round_seed()`; `update` takes it into a local and restores it at its end — no early return may sit between, a `debug_assert` at update's top catches violations). Both binaries take `--seed` (decimal or 0x-hex, `parse_seed` in lib.rs): the probe replays a round bit-for-bit; the game binary reproduces the same round setup and replays it identically on every R-key/auto restart (windowed *evolution* diverges over time under variable frame dt — probe↔probe is the bit-exact pair). A probe sweep derives round i's seed as base+i, prints the base in its header and each round's own seed in every `ANOMALY`/flagged-round line plus an end-of-sweep replay recap, and unseeded runs draw-and-print a base — so every run ever made is replayable. Guarded by `simulation.rs`'s `determinism_tests` (two seeds, 600 frames, run twice, bit-compared). Promote a nailed-down `(seed, scenario)` finding to a `#[cfg(test)]` in `simulation.rs` asserting the *behavioral* claim (not exact trajectories — RNG streams may shift across toolchain bumps) once it's worth locking in as a regression check.
  - **Capturing gameplay anomalies (stale/stuck/jittering tanks).** `probe.rs` also runs standing per-frame anomaly checks (`AnomalyTracker`/`check_anomalies`) against every enemy tank — scoped to enemies only, since the player's behavior is fully explained by the scripted `Scenario` already. Silent unless something trips; a hit prints one greppable `ANOMALY round=.. seed=0x.. frame=.. t=..s kind=.. tank=.. pos=(..) <detail>` line instead of requiring a full frame trace to be read — the `seed` makes every single anomaly line a self-contained replay recipe (paste into `--seed`). Twelve kinds so far, all tuned against real constants (`lib.rs`/`simulation.rs`) rather than guessed thresholds: `stale-start` (never got more than a few px from spawn at any point in the first 2s - judged on the farthest it got, so a tank that drove off and wandered back through spawn is not stale), `stall` (near-zero speed for 3s+ mid-round), `border-stuck` (parked within 40px of a battlefield wall — walls' inner faces sit exactly at 0/width/0/height, see `spawn_walls`), `jitter` (heading flip-flops A→B→A repeatedly within 2s — the exact failure mode `committed_dir`/`dir_hold` in `ai.rs` exist to prevent), `spin` (a full circle of *same-direction* quarter-turns within 2s with under ~60px of net drift — the "tank visibly rotating in place" failure, which `jitter` is structurally blind to since a rotation cycle contains no A→B→A triple), `churn` (300px+ of path driven inside a 4s window that ends under ~60px from where it started — full-speed "dancing", the complement of `stall`, which needs near-zero speed, and of `spin`, which needs rotation), `clustering` (at least `CLUSTER_MIN_GROUP` enemies mutually within `CLUSTER_RADIUS` of each other, sustained for `CLUSTER_FRAMES_THRESHOLD` — enemies piling up instead of spreading out across the engagement-slot system in `simulation.rs::Game::update`), `wall-grind` (driving into static terrain: `touching_static` with a nonzero move command sustained 2s — the failure `stall` can't see, since a grinding tank may still be moving), `bump-rate` (rising edges of terrain contact per trailing minute above a measured cap — "hitting obstacles too much", literally; threshold measured from real sweeps, table in the const's comment), `low-progress` (commanded > half top speed while achieving < 30% of it for 3s — intent-vs-outcome, ~4× the AI's own `STUCK_ESCAPE_SECONDS` so it fires only when the escape hatch is failing repeatedly), `never-arrived` (a live enemy whose spawn-time A* route existed — `Game::nav_path_cells` — but who never entered `ENEMY_ATTACK_RANGE` of the player within a grace-plus-4×-ideal time budget; trace mode prints a per-enemy route/ideal/stretch table, and the verdict runs once at round end), and `invariant` (frame-level physics sanity — non-finite position/velocity, escaped the battlefield bounds, speed above a generous cap; the one kind that also covers the player and wrecks, since a solver blow-up isn't explained by the scripted `Scenario`). **Deliberate-hold suppression**: `stall`/`stale-start` are muted for a tank that's standing still *on purpose* — fired within the trailing few seconds, currently holds an aligned in-range firing solution, or is waiting out a retreat recharge (`TankTrack::deliberate_hold`, fed by ammo/fire tracking in the snapshots) — added when the nav-grid rasterization fix made correctly-stationary firing tanks the norm and every one of them false-positived against an AFK player. Add a new anomaly kind by extending `TankTrack` + `check_anomalies` the same way; tune thresholds as named consts at the top of `probe.rs`, not inline magic numbers.
    **Known blind spot**: `jitter`'s A→B→A pattern-match can't tell rapid, wasteful flip-flopping apart from legitimate multi-leg weaving through a dense/maze-like obstacle cluster (each leg held a genuine ~0.3-0.5s, not a frame-to-frame flicker, when checked frame-by-frame with `--log-every 1`) - a high `jitter` count is not on its own proof of a real problem the way `stall`/`border-stuck` are; corroborate with a per-frame trace or an actual playtest before treating it as a regression.
  - **`--rounds N` for statistical coverage.** A single round has one random spawn layout and one AI RNG roll, so a bug that only shows up 1-in-N rounds needs many rounds to catch reliably. `--rounds N` re-`init`s the game N times (same as the game's own restart path) and, once N>1, suppresses the per-frame trace/`--log-every` entirely — only `ANOMALY` lines plus a one-line-per-flagged-round summary and a final aggregate print. This is the default way to go looking for stale/stuck/jittering-tank bugs: `cargo run --bin probe -- --scenario afk --enemies 4 --frames 900 --rounds 30` sweeps 30 independent rounds in about a second of wall-clock time (headless, no real-time wait) and reports only what's actually wrong. The harness's first major scalp: sweeps surfaced enemies stalling/spinning shortly into rounds, which was eventually root-caused (via the map linter's failure dumps + probe traces) to `Grid::build`'s old any-overlap rasterization stacking a hidden extra half-cell of margin — sealing much of the map into pockets whose unreachable waypoints made `Ai::wander` re-roll every frame. Fixed by the cell-center occupancy rule in `Grid::build` (plus `Ai::wander_pocketed`); sweep spin/churn counts dropped several-fold across scenarios.
  - **Sweep ergonomics** (Phase 6 of docs/gameplay-verification-design.md): `--json-out <file>` writes one JSON Lines record per round as it finishes (seed, map, all twelve anomaly counts, per-tank route/stretch/contact/distance stats — `path_cells: null` marks the no-route-at-spawn population); `--budget <kind>=<max>` (repeatable; kinds are the twelve ANOMALY tags plus `total`) exits 1 on any breach, 0 otherwise; `--heatmap` prints per-kind ASCII grids of anomaly positions at `PATHFIND_CELL_SIZE` granularity — its first render localized the default map's stalls to the walled top strip the linter had flagged. `just probe-sweep` is the standing default-map health check; `just probe-fixtures` (mirrored in `.github/workflows/ci.yml` alongside `cargo test --lib`) sweeps every fixture at a pinned seed against exact recorded ceilings — deterministic, so an exceedance is a real behavior change; the recipe's comment carries the re-baselining policy, and the definitive standing baselines live in the design doc's wave-5 close-out.

- **`src/maplint.rs` — static battlefield-map linter** (Phase 3 of docs/gameplay-verification-design.md; run `cargo test --lib maplint`). Exhaustive, provable checks over a map's finished static terrain, set up as a real seeded headless `Game::init` and read through the exact `Game::nav_grid` the AI steers by (occupancy queried via `blocked_ahead`/`boxed_in`, so the linter *cannot* disagree with what the AI sees). Five checks: playfield connectivity/reachability (frog + every pickup slot within approach reach; a pickup approachable only once destructible non-Iron walls are shot away is a `gated-pickup` *warning*, computed from a second flood fill over an Iron-only grid - Iron is the one permanent material), open-but-boxed-in cells, spawn-band capacity (the same legality predicate `Game::init`'s enemy sampler uses, counted per nav-cell center), planner-vs-physics agreement (grid-open cells a worst-case tank AABB physically can't occupy — the stuck-tank generator class), and single-cell-wide corridors. The gate `supported_maps_no_new_errors` permits only each supported map's recorded debt in `KNOWN_ERROR_KINDS` (error *kinds*, not counts — default.toml is a live editing canvas) and fails instantly on any new error class; `maps/test/` fixtures assert their intended lint profiles; every other `maps/*.toml` is lint-and-print only (`--nocapture` to see it). default.toml currently carries no lint errors: 28 of its pickup slots (the top-edge strip and the bottom-right rows) are `gated-pickup` warnings - not AI-reachable on intact terrain, but reachable once brick is shot away (the three health packs at the top center sit behind a permanent iron gate, breachable only through the brick columns beside it). (Its border band used to have zero legal spawn cells under an older, distance-based predicate; the shared `enemy_spawn_legal` predicate now counts ~40 there, so `spawn-band-too-tight` is no longer part of that map's debt.)

## Web / wasm build
The game also compiles to `wasm32-unknown-emscripten` and runs in the browser via `sola-raylib`'s `game_loop::run` (`main.rs`), which uses `emscripten_set_main_loop_arg` on web instead of the blocking `while` loop used on native. Full background: `../sola-raylib/book/src/web.md`.

- One-time setup: `just setup-web` — installs emsdk (pinned to 5.0.6 in `tools/setup_emscripten.sh`; newer versions have a wasm-opt bug, see the script) and the Astro site's JS dependencies (`cd site && yarn install`). The `wasm32-unknown-emscripten` rustup target and node/yarn themselves come from `devenv.nix`'s `languages.rust.targets`/`languages.javascript`, so a `direnv reload`/new shell after pulling `devenv.nix` changes is enough to get them.
- Build + run: `just build-web` then `just serve-web` (http://localhost:4321). `just build-web-dev`/`just serve-web-dev` do the same with `--features dev-tools` (note `serve-web` *depends on* `build-web`, so running it after a `build-web-dev` silently rebuilds without the feature and the panel vanishes - use `serve-web-dev`, or `just preview-web` to serve `site/dist/` as-is): the wasm exports the tuning C API and the page's **Tuning** panel appears under the canvas (docs/runtime-tuning-design.md). The panel is rendered entirely from the schema the wasm exports (`site/src/pages/index.astro`'s inline script), so a new `tunables!` row needs no site change; it shows itself only when `Module._bb_tuning_schema_json` exists, so a production wasm never has it. Edits persist in `localStorage` and are re-applied on reload; "Copy JSON" gives a `--tuning` file, "Copy as Rust" gives table rows to paste back into `tuning.rs`.
- **The site that ships the game is an Astro project at `site/`** (`site/README.md` has the full picture). Astro owns the page shell (`site/src/pages/index.astro` — port of the old hand-rolled `web/shell.html`, now deleted), styling, and any marketing content; it never builds or touches the game itself. `just build-web` does the Rust build first (`cargo build --release --target wasm32-unknown-emscripten`), copies `bongbong.{wasm,js,data}` into `site/public/game/` (gitignored — a build artifact, not source), then runs `yarn build` inside `site/` to produce `site/dist/`. That ordering matters: Astro's `public/` directory is copied byte-for-byte into `dist/` with no processing, which is required since Emscripten's glue JS looks up `bongbong.data` by a fixed relative path next to itself — hashed/bundled asset names would break it. Minification of the wasm/JS glue happens entirely on the Rust/Emscripten side (Cargo's release profile forwards `-O3` to `emcc`, which runs Binaryen's `wasm-opt` and Emscripten's own JS minifier) before Astro ever sees the files; Astro/Vite's own minification only covers its own build output (the page markup/CSS/scripts it actually processes). `wrangler.toml` deploys `site/dist/`, not `target/web/` (that staging directory no longer exists).
- `.cargo/config.toml` carries the emscripten linker flags (GLFW3, memory growth, `--preload-file static@/static` so `static/tanks.png`-style paths resolve unchanged) and an `[env]` block pinning `CC_wasm32_unknown_emscripten`/`CXX_wasm32_unknown_emscripten`/`AR_wasm32_unknown_emscripten` to the real `emcc`/`em++`/`emar` — **required under devenv/nix**, because nix's C toolchain module sets a global `CC` pointing at a host-wrapped clang that injects flags (e.g. `-fzero-call-used-regs`) `emcc` rejects for the wasm target; cc-rs picks the global `CC` over emcmake's own toolchain unless the target-specific env var wins. This bit isn't in sola-raylib's book (written for a non-nix host) — it's specific to this project's devenv setup.
- **Shaders need a GLSL ES 100 port for web.** raylib's `PLATFORM_WEB` build defaults to OpenGL ES2 (`raylib/cmake/LibraryConfigurations.cmake`), which only accepts GLSL ES 100, not desktop's `#version 330`. `static/web/{shockwave,muzzle_flash,impact}.fs` are hand-ported copies of `static/*.fs` — same logic, only syntax changes (`#version 100` + `precision mediump float;`, `in`/`out` → `varying`, `texture()` → `texture2D()`, `finalColor =` → `gl_FragColor =`). `main.rs`'s `shader_path()` picks the right directory via `cfg!(target_os = "emscripten")`. If a shader effect's logic changes, port both files by hand — there's no shared source.
- No audio yet, so the build skips `-sASYNCIFY=1`. The moment `InitAudioDevice`/sound is added, both `-sASYNCIFY=1` needs to go back into `.cargo/config.toml` rustflags (raylib's audio backend needs it) — `game_loop::run` alone won't cover it.
- **CI deploys, two lanes sharing one build:** `.github/actions/build-web/action.yml` is a composite action holding the CI web-build steps (the CI mirror of `just build-web`; the Rust/emsdk version pins live there as input defaults — keep in sync with `devenv.nix`/`tools/setup_emscripten.sh`). `.github/workflows/cloudflare-deploy.yml` uses it on version tags to `wrangler deploy` production (the `bongbong` Worker serving bongbong.io, static assets per `wrangler.toml`). `.github/workflows/pr-preview.yml` uses it on every PR (passing `cargo-features: --features dev-tools`, so **PR previews are the QA surface with the tuning panel; production never gets it**) to deploy an **ephemeral per-PR preview Worker** (`bongbong-pr-<N>`, played at **`pr-<N>.preview.bongbong.io`** — a Workers Custom Domain attached via a CI-generated `wrangler.preview.toml` (gitignored; `compatibility_date` is grep-read from `wrangler.toml`), since `custom_domain` routes can't be expressed as CLI flags; Cloudflare auto-creates the DNS record + per-hostname cert (pr-N.preview.\* sits below the universal `*.bongbong.io` cert, so first TLS can lag a minute — `workers_dev = true` keeps a workers.dev fallback URL, subdomain `otobrglez.workers.dev`), and never touches bongbong.io's own routes), posts/updates a sticky PR comment with the URL, and on PR close deletes the worker (`wrangler delete --name …` — removes the custom domain/DNS with it; a never-deployed worker is tolerated as already-clean). Both lanes reuse the same two repo secrets (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`); the custom-domain attach needs zone-scoped Workers Routes:Edit on top of account-level Workers Scripts:Edit — the live account token ("bongbong-token") already carries both (incl. a "Workers Routes Write on all zones" policy; verified in the dashboard 2026-08-27), and DNS/certs for custom domains are Cloudflare-managed so no DNS:Edit/SSL:Edit is required. Fork PRs get no secrets under `pull_request`, so previews are same-repo-branch only by design — never "fix" that with `pull_request_target`.

## Releases (cargo-dist)
Native binary releases (macOS x86_64/aarch64, Linux x86_64, Windows x86_64 — deliberately *not* the wasm/web build, which stays on its own `just build-web`/`serve-web` path above) are built and published to GitHub Releases by `.github/workflows/release.yml`, generated by [cargo-dist](https://opensource.axo.dev/cargo-dist/) (`dist-workspace.toml`; `[profile.dist]` in `Cargo.toml`). Triggered by pushing a tag matching `v{X}.{Y}.{Z}` — bump `Cargo.toml`'s `version`, tag it to match (`git tag v0.0.8 && git push --tags`), CI does the rest.
- **`static/` ships bundled in every release archive**, not embedded in the binary. `main.rs` loads textures/shaders by path relative to the process's *working directory* (`"static/scifi_tanks_sheet.png"` etc.), not the executable's location, so a downloaded release only works run from the folder it was extracted to. `dist-workspace.toml`'s `include = ["static"]` handles the bundling; if this ever needs to work from an arbitrary CWD (e.g. a PATH install), the fix is resolving asset paths against `std::env::current_exe()` instead — not done, since no installer needs it yet (see below).
- **No installer scripts** (`installers = []`) — this is a windowed game people download and run, not a CLI tool anyone wants on `$PATH`, so releases are plain per-platform archives only (no `curl | sh`/PowerShell/homebrew).
- **`probe` ships in every archive alongside `bongbong`, and there's no clean way to stop it.** cargo-dist has no per-binary exclusion within a single package — only a package-level `dist = true/false` for workspaces with multiple crates. Splitting `probe` into its own workspace member would fix this but wasn't judged worth the restructuring for a small headless debug tool with no sensitive content; revisit if it ever grows large or gains anything not meant for end users.
- **Linux needs raylib's system dev packages** (`[dist.dependencies.apt]` in `dist-workspace.toml`) — X11/OpenGL/audio/input headers, since raylib-sys builds from source. Same package list as `../sola-raylib`'s own working CI (`../sola-raylib/.github/workflows/ci.yml`), not assembled from general advice. macOS/Windows runners need nothing extra.
- **No `LICENSE` file yet** (left out deliberately for now) — cargo-dist works fine without one, but revisit before any installer type that surfaces it (homebrew formula, etc.) gets added.
- `dist generate --mode ci` regenerates the workflow after editing `dist-workspace.toml`. One local gotcha: **`--allow-dirty` silently no-ops the actual file write** in this cargo-dist version (0.32.0) — `dist plan`/`dist generate` report success either way, but only the run *without* `--allow-dirty` actually writes `.github/workflows/release.yml`. Also make sure `.github/workflows/` exists first (`mkdir -p`) — `dist generate` doesn't create the directory itself.
