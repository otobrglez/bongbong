# bongbong

Bongbong is a tank shooter game. Main purpose of this game is to be a fun, fast and entertaining game where player shoots other tanks. Artisticly the game trys to be "pixelated" and it tries to mimic old tank arcade games. The twist of this game is to have semi-realistic physics, intersting and challenging AI and ability to build your own battlefields.

# Architecture & Development

- This application is written in Rust.
- The main library it uses is Raylib (written in C) but not directly it uses sola-raylib wrapper/bindings designed to work well with Rust. Source code for raylib in C is available at `../raylib`.
- Game uses sola-raylib bindings for Raylib. Source code for sola-raylib is available at `../sola-raylib`. When needed you can always consult this source code and its wide collection of examples.
- The game uses rapier physics game engine written in Rust. The source code for engine is available at `../rapier`. When working on physics consider consolidating the source code.
- Dependencies and environment is isolated with the help of devenv (Nix) so there is `devenv.nix` and `.envrc` that has some credentials and it defines Rust versions etc.
- For faster development loop developer runs `cargo watch -x "run"` that watches for source changes, compiles project and boots the application. This gives developer better overview.


# Game structure
- Main entrypoint is `src/main.rs`
- Assets, sprites, shaders etc live inside `static/`
- Tools / scripts and other things needed for the development live inside `tools/`

## Module map
- `main.rs` — entrypoint: window/texture/shader setup, owns the raylib handle, the main loop and the `mode::Session` (the round and the map builder, whichever is live). The loop body branches on `Session::mode()`: in Play it gathers each frame's raw input into a `simulation::Input` and passes it to `Game::update`; in Build it gathers a `editor::BuilderInput` (the pointer - mouse, or the first touch point, edge-detected by hand because raylib reports a held finger as a point count - press/held for the primary and right buttons, the wheel, `Tab`/`Esc`/`Enter`/`Backspace`, Ctrl/Cmd+Z/Y, typed text) and hands it to `Session::update_builder`, then renders the builder and returns — nothing past this file ever touches `RaylibHandle` for input. The `BUILD` button (`hud::mode_button_rect`) and the leave dialog (`hud::leave_dialog_rects`) are handled before the frame's `Input` is gathered, and `Session::playing` is false while the dialog is up, so neither the loop nor the dev server's `advance` calls `update` - the round is frozen by construction, no simulation flag involved. `Tab` is `Session::toggle`. `--editor` means "start in Build": the round is initialised exactly as usual and only `session.driver` starts on the builder, so `PLAY` has everything it needs; there is no feature gate, the builder compiles into every build. `builder.cli_overrides` is filled from `Args` so the MAP panel can mark a row `(cli)` when a flag will outrank the map's value at PLAY. **The window is the battlefield plus the HUD bar** (`Layout::for_field(w, h).window_size()`, docs/hud-and-builder-layout-design.md): `--resolution` and `DEFAULT_SCREEN_WIDTH/HEIGHT` mean the *field*, which is all `Game::init`/`update`, `RippleFx::load`, `scene_target` and the dev server ever see; a window press is shifted into the field by `Layout::to_field` before a dialog hit-test sees it. A press on the field itself is not an input in play mode - there is no pointer control of the tank. The version string is in the window title as well as bottom-right of the field (`hud::version_line`). **Two players** (docs/two-players.md): `gather_intents` builds both `Input` intents per `Game::players` (single: arrows + Space; two: arrows + Right Shift and WASD + Left Shift), `--players 1|2` and `--tank2` set `Game::players`/`player2_row_override` before `init`, the pre-input block also hit-tests the players dialog (`hud::players_dialog_rects`; keys 1/2, Enter = the other count, Esc/Tab close) and the players button (`hud::players_button_rect`). `shift_state` is the one `cfg(target_os = "emscripten")` fork: the web reads `window.bbShift` through `emscripten_run_script_int` because emscripten's GLFW maps both Shift keys to the left one.
- `lib.rs` — shared *layout* constants and types (`Position`, sprite-atlas columns/sizes, `*_VARIANTS`, collider bounding boxes, grid/physics sizes, and `HUD_BAR_HEIGHT`/`Rect`/`Layout` - where the field and the HUD panel sit in the window; the field origin is `(0, 32)` and nothing but `game.rs`, `editor/` and `main.rs` cares; the builder's popup geometry - `EDITOR_DROPDOWN_ROW_H`/`EDITOR_DROPDOWN_W`/`EDITOR_SETTINGS_W`/`EDITOR_STEPPER_SIZE`, the 48 px finger targets, `EDITOR_BAR_HIT_SLACK` and the `EDITOR_PANEL_*` chrome - is layout too and lives here). Heavily commented inline — treat those comments as the source of truth over restating them elsewhere. **Gameplay/feel knobs no longer live here**: everything that's a design decision rather than an asset description (speeds, forces, damage, fire intervals, AI ranges, cosmetics, shader FX) moved to `tuning.rs`'s table in 2026-09 — don't add a new `pub const` knob here, add a row there.
- `tuning.rs` — the runtime-tunable knob table (docs/runtime-tuning-design.md): one `tunables! { group x { /// doc  name: ty = default in min ..= max [labels NAMES] [@ Live|Spawn|Restart]; } }` row per knob (~235 rows in 18 groups), expanded by a `macro_rules!` into the `Tuning` struct, `Tuning::DEFAULT`, the static `Tuning::SCHEMA` (name/group/type/doc/range/labels/applies - the doc comment is *captured*, so it's what the dev panel shows), and range-checked `get`/`set` by name (`name`, or `name.label`/`name.<i>` for an array row like `wall_max_health: [f32; 4] labels MATERIAL_NAMES` / the `[f32; 12] labels TANK_NAMES` per-chassis tables, indexed by `material as usize`/`tank.row`). Read everywhere via `tuning().field` (a global `RwLock` read guard - bind once in hot loops). **Writes only at the frame boundary**: transports stage a patch (`submit_json`/`submit_reset`, or `submit_file` for `--tuning <file>`) and `main.rs` calls `apply_pending()` right before `Game::update`, so a frame never sees two values of one knob and nothing in `simulation/` ever mutates tuning; `request_restart`/`take_restart_request` is how the panel's Restart button becomes an `Input::restart_pressed`. Derived values (`engage_ring_radius()`, `enemy_retreat_range()`, `minigun_burst_cooldown_seconds()`) are methods, not rows, so they track their base knob. `Tank::speed` became `Tank::speed_scale` (a per-tank factor) so `tank_speed`/`enemy_speed` are live mid-round; `RippleFx::set_tuning` re-uploads the shader uniforms when the table changes. Unit tests (`cargo test --lib tuning`) cover the macro, JSON patch/diff round-trip, and "Copy as Rust" output; they work on local `Tuning` values only - never mutate the global in a test, the suite runs in parallel threads.
- `capi.rs` *(feature = "dev-tools", dev/QA-only)* — the `extern "C"` surface over `tuning.rs` (`bb_tuning_schema_json`/`_current_json`/`_diff_json`/`_diff_rust`/`_apply_json`/`_reset`, `bb_game_restart`, `bb_last_error`) that the web page's tuning panel calls through `Module.ccall`. Returned strings live in a thread-local scratch buffer valid until the next `bb_*` call. `main.rs` calls `capi::keep_alive()` so the functions are actually referenced from the binary, and `build.rs` emits `-sEXPORTED_FUNCTIONS=_main,_bb_...` for the `bongbong` bin only, only on `wasm32-unknown-emscripten` with the feature on (`capi::EXPORTS` and the `build.rs` list are checked against each other by a unit test).
- `devserver.rs` *(feature = "dev-tools", native only - gated `not(target_os = "emscripten")`, dev-only)* — the embedded local dev server (docs/dev-server-design.md): newline-delimited JSON on `127.0.0.1:4747` (`--dev-port`/`BONGBONG_DEV_PORT`, `--no-dev-server`), serviced by `main.rs` at the frame boundary exactly like the tuning transports (socket threads only queue `Request`s over an mpsc channel; `before_frame` and `dispatch` take the whole `mode::Session` and drain them, `advance` - still a bare `Game` - owns the update call, `after_render` takes screenshots) so nothing ever touches `Game` mid-`update`. **The two modes and the builder are tools too** (docs/dev-server-design.md 4.1): `mode`, `build {answer}`, `play {intro}`, `builder_tool {tool}`, `builder_paint {cells, tool, button}`, `builder_undo`/`builder_redo {steps}`, `builder_settings {tanks, tank, mission, spawn, waves, ..., reset}`, `builder_map {map_toml | map}`, `click {x, y, button, drag_to}` (window pixels, bar included - the same hit-tests a mouse gets, in either mode) and `key {key, text}` all go through `Session`'s methods and the builder's `BuilderInput`, so a tool and a click are the same path. `GAME_ONLY_TOOLS` (`snapshot`, `events`, `step`, `input`, `pause`, `resume`, `history`, `nav_grid`, `teleport`, `set_tank`, `kill`, `spawn_enemy`) are refused in build mode with an error naming `play` rather than touching a frozen game; `status` (now also `mode`, `dialog_open` and `builder {dirty, tool}`), `screenshot`, `overlays`, `map_get` (the *round's* map, which differs from `builder_map` once the builder is dirty), `tuning_*` and `restart` work in both - `restart` always returns to play and with a `map`/`map_toml` replaces the builder's canvas and baseline as well (`Session::replace_map`). `play` does what `restart` does afterwards (banks `round_started`, restarts the history ring, enters lockstep), so the `step`/`screenshot` loop carries over unchanged. Owns **lockstep**: `step {frames}` freezes real-time advance and runs N `Game::update`s at `PHYSICS_FIXED_DT` inside one rendered frame (fast, bit-for-bit replayable from `restart {seed}`, which itself leaves the new round frozen); `pause`/`resume` toggle it. Screenshots are captured one rendered frame after the request because raylib's screen read-back lags the buffer swap - the same frame in lockstep. `TOOLS` is the single tool table (name/description/JSON schema) that `bin/bbmcp.rs` advertises over MCP, so adding a tool means one `ToolSpec` row plus a `dispatch` arm. `restart {map_toml}` starts a round on inline map TOML (no file needed; `map_get` returns the current map's TOML to edit and resubmit; `status.map` names what is loaded). `events`/`step` take `kinds`/`exclude` name filters (the ring is 4096 because the AI-decision events are chatty; `before_frame` sets `Game::trace_ai` so they are recorded at all). A **history ring** records every live tank's `debug::TrackRow` after each update (3600 frames, cleared when the frame counter goes backwards, i.e. a restart) and the `history` tool returns sampled rows plus per-tank aggregates (distance, net displacement, cluster/stuck/no-ring/touching frame counts) - the live counterpart of the probe's `TankTrack`. `input {cycle_overlays: true}` presses the I key for one frame, so the preset cycle is reachable from the tools too. Unit-tested headlessly through `DevServer::headless()` (`cargo test --lib --features dev-tools`). **Two players** (docs/two-players.md): `players {count?}` (game-only: press the button, or answer the dialog - a new count restarts and `round_started` re-enters lockstep), `restart {players, tank2_row}`, `step`/`input` take `p2_move_dir`/`p2_face`/`p2_fire` (`parse_intent(params, "p2_")`, `injected2`, `PendingStep::intent2`), `status`/`mode` carry `players` and `players_dialog_open`, `click`/`key` mirror `main.rs`'s players dialog and button (keys `1`/`2`), `builder_settings {tank2}`. `bin/bbmcp.rs`'s instruction string notes the slot rule: 0 = player 1, 1 = player 2 in a two-player round, enemies from `Game::first_enemy_slot`.
- `bin/bbmcp.rs` *(`required-features = ["dev-tools"]`, and left out of `dist-workspace.toml`'s `[dist.binaries]` list, so never in a release archive - a release build has no such bin, and dist would fail looking for it otherwise)* — the stdio MCP adapter Claude Code launches from the repo's `.mcp.json` (`initialize`/`ping`/`tools/list`/`tools/call`; one request line to the game per call; screenshots come back as `image` content; an unreachable game is an `isError` result naming `just run-dev`, never a crash). Also `bbmcp call <tool> [json]` for shells (`just mcp-call`). stdout is protocol only - log with `eprintln!`. Has a stub `main` for emscripten because the wasm dev build compiles every bin.
- `simulation/` — the simulation layer, a directory module (`crate::simulation` paths are unchanged). `mod.rs` owns `Game` (state, `Game::init`, and `Game::update` as a sequence of named phase methods - the frozen mission intro (`intro_timer`, only while `show_intro`, which the windowed game sets and headless callers leave off), timers, frog (both frogs), pickups, player, roll-in, enemies, waves, lasers, `step_world`, ram, shell-vs-shell, projectile hits, explosions (a kill lays down a fireball, a whole-screen flash, a scorch, several thrown `decal::Decal` parts and a queue of delayed ammo cook-offs - `Game::wreck_fx` / `tick_cookoffs` / `Event::CookOff`, every angle, arc and delay hashed from position so a spectacular death still draws no RNG. The flash is explicit state, `Game::screen_flash`, started only through `Game::flash_screen` by kills and barrels and spaced at least `blast_screen_flash_min_gap_seconds` apart so a barrel chain or a multi-kill flashes once instead of strobing; a cook-off is local - a small `BlastFx::small` fireball marked `secondary`, a faint `SHOCK_COOKOFF` ripple and sparks - and never flashes the screen, punches an impact quad or shakes the camera), cleanup, round end - sharing a per-frame `Frame` context that carries the round RNG, the terrain snapshot and everything spawned/applied only once no query is active). `weapons.rs` fires shots and ticks queued twin-barrel/burst shots (`dispatch_fire`/`tick_queued_shots`, shared verbatim by player and AI) and defines the `Projectile` trait that lets one hit loop serve shells, bullets and plasma. `hits.rs` is the **only** projectile hit test: `Terrain` (a per-frame snapshot of seam-closed obstacle boxes, frog and walls) plus `Terrain::sweep`, a nearest-entry-time segment-vs-box sweep over each projectile's whole movement this frame (wrecks are skipped - a hulk used to absorb shells while `apply_hit` discarded the damage, a free bullet sponge the AI could not see as cover either) - projectiles have no physics body and rapier is not consulted for hits; `Terrain::line_of_sight` is the AI's fire gate. `combat.rs` applies a resolved hit (`Game::apply_hit`: damage, knockback, frog hop, `Ai::notify_hit`), `ram` (wrecks neither deal nor take ram damage; impact speed is the closing component of the bodies' *real* velocities, not the commanded `Tank::velocity`, which is a fixed-magnitude cardinal vector that says "both are driving" rather than how hard they hit) - run for every enemy against the player *and*, via `Game::ram_enemy_pairs`, for every enemy pair (sorted by owner slot and walked i<j so the RNG draw order is fixed, with a distance cull before the narrow-phase query since it is O(n^2) in live enemies) and explosions. `engage.rs` is the engagement-slot ring (`EngageRing`, unit-tested with closures; reachability comes from one `Grid::components` flood fill per frame, not per-candidate A*); `assign` also fills an `EngageReport` (per enemy: `EngageStatus`, the `EngageSlot` held - `index()` 0-15 - its target, whether it was sticky, and a `Rejections` tally of claimed/off_map/unreachable/no_los candidates; plus the 16-slot table with memoised line of sight) that `Game::last_engage` keeps for the overlay, the snapshot and the AI event diff - see docs/dev-server-design.md "Debugging enemy clustering". `debug.rs` is the tooling surface on `Game` the dev server calls between frames (`debug_snapshot`/`DebugSnapshot` with plain `x`/`y` fields since `Vector2` isn't `Serialize`, `debug_teleport` through `Physics::set_position` plus a collider re-orient, `debug_set_tank`, `debug_kill` - queued into `Frame::kills` so it explodes and ends the round like a real kill - `debug_spawn_enemy`, the one mutator that draws round RNG, `nav_grid_ascii`, `debug_track_rows` - the cheap per-frame rows the dev server's history ring stores - and `clusters`/`CLUSTER_RADIUS_PX`, shared with the probe's clustering anomaly). `mod.rs` also keeps the **event log**: phases push `Event`s (fired, hit, wreck, ram, shield deflection, shell-vs-shell cancel, frog bite, pickup collected/respawned, round started/ended, and - only while `Game::trace_ai` is set, which nothing but the dev server does - the AI decisions `ai_action`/`engage_slot`/`stuck_escape`/`breach`/`retreat`/`alert`, produced by `enemy_phase` diffing each enemy's `AiSnapshot` around its `think` and the `EngageReport` against last frame's, so `ai.rs` stays snapshot-only) onto `Frame::events`, merged into `Game::events` and cleared at the top of each `update` - free for determinism (no RNG), read by the dev server and by `mechanics_tests` (assert on `game.events()` instead of diffing snapshots) - plus `Game::frame` (updates this round) and `Game::debug_overlays` (`Overlays`: the inspect readout plus five more flags `game.rs` draws in dev builds; `next_preset` is the I-key cycle). No `RaylibHandle`/drawing dependency by design — driving a round forward needs nothing but this module and a `simulation::Input`. Projectiles are integrated inside the fixed-step loop with the physics step, and on the end screen they still fly and land (without damage) while the restart counts down. **Two players** (docs/two-players.md, tests in `simulation/two_player_tests.rs`): `Game::players: PlayerCount` (a pre-init setting kept across restarts), `player2: Option<Entity>` beside `player` with `players()`/`player_index`/`is_player`/`first_enemy_slot` accessors, `Input::player2_intent`, per-player fire edge state, `player_phase` -> `drive_player` per player (a wrecked player is left alone), one `EngageRing` per player, and `enemy_phase`'s retarget pass (`Ai::target_player`: the nearer live, unconcealed player, hysteresis `enemy_target_switch_margin_px`, `Event::Retarget`; only run with two players). `Tank::owner: Owner` (`Owner::Player(u8)`/`Enemy(slot)`) is stored, `owner_slot()` derived; `Frame::kills` carries the victim's `Owner`; `hits::ShellTarget::Tank(Entity)` replaced the player/enemy split and `Terrain::sweep` takes `Game::players()`; `apply_hit`/`ram` scale player-on-player damage by `friendly_fire_damage_factor` after the roll; `apply_explosion`/`apply_blast`/`sync_tanks_and_ram` walk players in index order then enemies, so a single-player round's RNG stream is unchanged - `just probe-fixtures` and a JSON diff of every fixture's probe records were held byte-identical through the whole change.
- `simulation/props.rs` — the props' rules, kept out of `combat.rs` so it stays the one place an obstacle loses health: `Game::damage_obstacle` (fence: amount-blind, pristine dies at `fence_one_shot_chance` odds else drops to damaged, damaged always dies; barrel in a blast: lethal but on a `barrel_fuse_seconds` fuse so a chain cascades visibly, a direct hit or ram pops it at once; everything else `Obstacle::damage`), `apply_blast` (everyone in `barrel_blast_radius` - both sides, frogs, tiles - takes falloff damage and knockback via `combat::explosion_hit`, which now takes a `BlastParams` so a wreck's and a barrel's blast share it; pushes `f.shock`, an impact flash, a `BlastFx` and a `Scorch`), `tick_burns` (advances every burning wood tile and routes the ones that finish charring through `obstacle_died` - wood is the only material whose death does not go through `damage_obstacle`, and before this it emitted no `Event::ObstacleDestroyed` at all and left nothing behind), `tick_fuses`, and `ram_props` (a live tank with a commanded move in narrow-phase contact - `Physics::touching` - with a sandbag/fence accumulates its `ram_timer` until `Material::ram_seconds`; a barrel takes `barrel_ram_damage_per_second`). `explosions` drains `Frame::kills` and `Frame::pending_blasts` as one worklist; on the end screen fuses still tick and blasts play visuals-only. Pass-over lives in `resolve_projectiles`: the sweep is re-run past any prop the projectile rolls a `pass_over_chance` on, remembered on the projectile (`Projectile::passed_over`, `Terrain::sweep_ignoring`) so a segment ending inside the tile doesn't re-roll; barrel deflection is the `deflect_chance` branch next to `try_ricochet` (`Projectile::can_bounce`/`reflect_off`; plasma never bounces). Zero-chance materials draw no RNG, so prop-free maps replay unchanged. Events: `ObstacleDestroyed { material, x, y }` (any tile death) and `Blast { x, y, chained }`; `HitTarget::Obstacle` is unchanged. Tests in `simulation/props_tests.rs` (statistical over seeds, since tests can't touch the global tuning).
- `simulation/waves.rs` — the Waves spawn plan at runtime (docs/maps-to-levels.md): `WaveState`/`wave_phase` (first wave on the first playing frame, the next when live enemies drop to `wave_next_when_alive` with the queue empty or after `wave_timeout_seconds`, then a `wave_gap_seconds` breather with the `WAVE N` banner; per-tank spawn rolls share `roll_enemy_tank` with `Game::init`, so the RNG draw order matches), `RollIn`/`rollin_phase` (a wave tank spawns *outside* the battlefield at a `battlefield::Gate` with `Tank::body == None` and **no `Ai` until it arrives**, so every `.with::<&Ai>()` query - hits, ram, engage rings, AI, round end - excludes it for free; it moves kinematically along the gate lane and gets its body, its `Ai` with a freshly rolled role, and `Event::TankEntered` on arrival), `despawn_wrecks` (wave rounds only, `wave_wreck_despawn_seconds`, `Event::WreckRemoved`), `wave_status` for the dev server, and the monotonic owner-slot counter (`take_slot`; the 31 is a cap on *live* enemies, `wave_max_alive`, not on a round's total). Gates are recomputed from the live grid at every spawn and a gate-less map falls back to the band sampler so a round never stalls.
- `battlefield.rs` — static terrain *placement* for a fresh round: boundary walls (`spawn_walls`), wave gates (`Gate`, `gate_candidates`: an edge nav cell whose `wave_gate_inward_cells` cells inward are open and whose lane clears the boundary walls, at least `wave_gate_min_player_dist` from the player/frog; `gates_from_cells` for a map's explicit `gate` cells) and the loaded `map::MapFile`'s walls/road/frog/pickup-slots (`spawn_from_map`), plus enemy placement: `sample_clear_position` (bounded rejection sampling, `None` on the attempt cap - callers then snap a sample to `Grid::nearest_open`, never use a rejected sample), `enemy_spawn_legal` (the one spawn-legality predicate, shared with `maplint.rs`'s spawn-band capacity count: border band + player clearance + a `Grid::usable` nav cell + a worst-case tank box clear of every wall tile - there is no separate `OBSTACLE_CLEAR`-style distance term any more, it made the default map's band unsatisfiable), `relocate_unusable_spawns` (post-layout audit that moves any enemy whose cell is blocked or boxed in) and `max_tank_avoidance_radius` (the clearance margin obstacle placement, spawn legality and the per-frame pathfind grid all use). `simulation/mod.rs`'s `spawn_tests` lock in that no enemy starts overlapping a wall on the default map. There is **no procedural fallback battlefield any more** — a map (`-m`/`--map`, or `maps/default.toml` when none is given, see `main.rs`) is the only source of static terrain; the old random "HELLO"-fortress/scattered-obstacle-structures generator was removed outright, not just made optional. The obstacle *entity type* (`Obstacle`) and the decorative ground layer (`ground.rs`) stay in their own modules; this one only decides where things go.
- `level.rs` — what a map asks of a round beyond terrain (docs/maps-to-levels.md): `Mission` (Protect/Hunt/Destroy - what ends the round, `Mission::banner` is the opening text), `SpawnKind`/`SpawnPlan` (Band: everyone placed at init; Waves: `wave_size(i)`/`wave_tier(i)` from `size + i*growth` and a linear tier ramp), `Tier` (light/medium/heavy/super - `TANK_TIER_BY_ROW` in `lib.rs` groups the 12 chassis rows; `Tier::rows`), the map tables `MissionConfig`/`SpawnConfig`, and `LevelOverrides` (one field per `--mission`/`--spawn`/`--waves`/`--wave-size`/`--wave-growth`/`--tier-start`/`--tier-end` flag, shared by `main.rs`, `bin/probe.rs` and the dev server's `restart`), resolved once in `Game::init` as CLI > map > the `waves` tuning group. Pure data, unit-tested.
- `map.rs` — the on-disk battlefield map format (`MapFile`/`CellObject`, TOML under `maps/`; `to_toml_string`/`from_toml_str` are the in-memory pair the dev server's `map_get`/`restart {map_toml}` use, and `MapFile::name` is a display-only label - file stem, `"default"`, or `None` for inline text - never serialised) and the grid↔world coordinate conversion (`cell_to_world`/`world_to_cell`) both `battlefield.rs` and `editor/` share. `MapFile` derives `Clone` and `PartialEq`, which is what lets the builder keep a baseline copy and diff the canvas against it. A map only encodes *interior* terrain (walls, the three props as `kind = "sandbag"|"barrel"|"fence"` cells and the two trees as `kind = "tree"|"pine"` - `CellObject::material()`/`is_solid()` fold them in with walls wherever a solid tile matters, e.g. `nearest_free_cell` - `kind = "tall_grass"`, which is deliberately *not* solid, road, one frog, health/ammo pickup slots) plus two top-level defaults — `tanks = N` (enemy count) and `tank = "titan"` (the player's chassis, a `tank::TankKind` name) — while border walls and enemy/player spawns stay procedural on top of it. Both defaults are outranked by the matching CLI flag (`-e`/`--enemies`, `--tank`); the chassis additionally sits under the `player_tank` tuning knob (`simulation::resolve_player_row` is the one precedence chain, CLI → knob → map → random roll). See docs/map-editor-design.md. Level data rides along: `mission`/`spawn` tables (`level::MissionConfig`/`SpawnConfig`, both `#[serde(default)]`, **written as dotted keys** `mission.kind = "hunt"` / `spawn.kind = "waves"` in hand-authored files because a `[spawn]` header would swallow every `cells.` line after it) plus two more cell kinds: `enemy_frog` (the Hunt mission's second frog, singleton, `enemy_frog_cell`) and `gate` (a wave roll-in lane on a nav-grid edge cell, `gate_cells`; any gate cells replace the automatic edge scan). `maps/missions/` holds one clean fixture per combination (`hunt-basic`, `waves-basic`). Two-player rounds add `CellObject::Start2` (`kind = "start2"`, `start2_cell`, singleton like `Start`) and a top-level `tank2 = "..."` key (`MapFile::tank2`), both read only under `Game::players == Two`; older files parse unchanged.
- `mode.rs` — the two modes and the switch between them (docs/game-editor-fusion.md section 5): `Session { driver: Driver, game: Game, builder: MapEditor, dialog: bool }` owns the round and the builder for the whole windowed session (both share the loaded textures) and `Driver { Play, Build }` says which is live. Both the window and the dev server go through its methods, so a tool and a click are the same path: `press_build` (the `BUILD` button or `Tab` in play: opens the leave dialog while `round_in_progress`, switches at once on the end screen, and pressed again while asked means keep playing), `answer_dialog(leave)`, `play` (`PLAY` from the builder: `game.map = builder.map().clone(); game.init(...)` - a fresh round on the edited map, a `--seed` staying pinned, the banner as on any restart; there is no resume, confirming BUILD gave the round up), `toggle` (`Tab`, either way), `replace_map` (the dev server's `restart {map, map_toml}`: sets the game's map and the builder's canvas and baseline), `update_builder` (one builder frame, turning `EditorAction::Play` into `play`) and `play_chrome` (the `PlayChrome` flags `Game::render` draws). `playing()` - play mode with no dialog - is the one predicate deciding whether `Game::update` runs this frame; the leave dialog is not a simulation pause, the round is just not advanced. `Deref`/`DerefMut` to `Game`, so the dev server, its tests and `main.rs` call `Game`'s accessors on a `Session` directly. No `RaylibHandle` in this file. `session_tests` cover the dialog mid-round vs the end screen, PLAY building the round from the edited map with the edit surviving the round trip, and `replace_map`. **The players dialog** is a second modal on `Session` (`players_dialog`, never open with `dialog`): `press_players` (the button, a toggle; a no-op while the leave dialog asks), `close_players_dialog`, `answer_players(count)` - a different count restarts via `game.init` (the R path, so the seed stays pinned), the same count just closes; `playing()` is false while either dialog is up; `press_build` while it is open just closes it. The count itself lives on `Game::players`, which every `init` keeps - that is what makes it the session's setting.
- `editor/` — the map builder, the game's **Build mode** (docs/game-editor-fusion.md; docs/map-editor-design.md for the data model and file format). Compiles into every build, release and web included - there is no feature gate; `mod.rs` owns `MapEditor`, `history.rs` the undo stack. Presentation-layer only, like `game.rs`: it edits the *authored* `MapFile` the round was built from (`mode::Session` seeds it once from `Game::map` at startup and never reseeds it, so edits survive a PLAY/BUILD round trip; only `Session::replace_map` swaps it), never the live entities. **Input arrives as a plain `BuilderInput`** (window-pixel pointer, `pressed`/`held` for the primary button and the right one, `wheel`, `escape`/`enter`/`backspace`/`undo`/`redo`, `typed`) that `main.rs` gathers once per frame the way it gathers `simulation::Input`, and that the dev server's `click`/`key`/`builder_*` tools fill the same way - so a tool lands on the same hit-test a finger does and `editor_tests` run headlessly; only `render` needs a `RaylibHandle`. The edit model every input path shares: `Tool` (the 23 brushes in bar order, `TOOLS`; `name`/`parse` are the spelling the dev server uses, `object()` the `CellObject` painted, `is_singleton()` for start/frog/enemy frog, which *move* rather than duplicate) grouped into five `Category`s (WALL/PROP/GROUND/ACTOR/PICKUP), each remembering its current tool for the session (`current_tool`/`select_tool`/`cycle_tool` - the wheel over a category button; the eraser belongs to none). A **stroke** is one press-drag-release that paints once per cell crossed (`stroke(cells, right)` for the tools, `begin_stroke`/`stroke_to`/`finish_stroke` for the UI frame by frame) under the **toggle-erase rule**, decided on the first cell and held for the whole drag: the right button, the eraser, or a first cell already holding *exactly* the brush's object makes it an erase stroke, anything else a paint stroke that never erases - so a drag across a row of bricks with the brick brush is all paint or all erase, never a checkerboard. Every completed stroke, each settings field, a load and a reset is one `EditStep` on the `UndoStack` (`history.rs`: `Cells` of per-cell before/after, undone in reverse so a cell touched twice lands on its original; `Settings { before, after }` over `MapSettings`, the map's `tanks`/`tank`/`mission`/`spawn`/wave keys as one copyable value with `changed_fields`; `Map` for a whole replacement, which keeps the display name; `UNDO_DEPTH` = 200, a new edit drops the redo branch, an empty stroke is not a step; Ctrl/Cmd+Z/Y and the bar's buttons). `load` replaces canvas *and* baseline as one step (`builder_map {map_toml}`, `load_named` for a Load-list name), `reset` reverts to the baseline, and `dirty` is `!diff().is_empty()` against it (`MapDiff::between`: cells added/removed/changed plus the settings that differ): dirty means "differs from the map as loaded or last saved". `apply_settings` clamps (tanks to `wave_max_alive`, waves 1..=20, size 1..=31, growth <= 10) and records nothing for a no-op. The chrome on top: the bar is **fixed slots** (`SLOT_*`: the `BUILD` label in `BUILD_ACCENT`, the map name with ` *` while dirty, five category buttons showing the current tool's 32 px icon plus name and caret - the icon half selects, the caret half opens the list - the eraser, `UNDO`/`REDO` dimmed when their side is empty, `MAP ▾`, `FILE ▾`, `MAP ▾`, the cursor readout `col,row <object>` for the hovered cell with a mouse or the last tapped cell on touch, and `PLAY` in `hud::mode_button_rect`; `bar_slots_fit_the_default_bar_without_overlapping` pins them). One `Popup` at a time - a category `Dropdown` of 48 x 200 px rows, the `File` menu (`LOAD...` everywhere; `SAVE`/`SAVE AS...` only where `map::saving_available`, i.e. native), the `Load` list (a centred panel of 48 px rows over every `map::available_maps` entry - the `maps/*.toml` files on native plus the `map::SHIPPED_MAPS` embedded in the binary, marked `shipped`, which is all the web build can list; twelve visible, the wheel scrolls; a pick is `load_named`: one undo step and the new baseline), the MAP `Settings` panel (340 px, a `SettingsRow` per map key with 48 px `<`/`>` steppers, `auto` = `None`, the wave rows dimmed under a band plan but still editable, a row marked `(cli)` when `CliOverrides` says a flag outranks it, and `RESET MAP`), or the `Save`-as prompt - opening one closes the others, `Esc` closes, and a press outside an open popup closes it and is **consumed**, so a tap to dismiss a menu on a phone cannot paint through it. `open_menu` names the open popup for the dev server's `mode` reply. Every bar button's hit rect reaches `EDITOR_BAR_HIT_SLACK` above and below its drawn box (`hit_rect`) because the 32 px bar is ~21 CSS px on a phone. `save(name)` writes `maps/<name>.toml` (`SAVE` reuses the map's name, `SAVE AS...` prompts; letters, digits, `-`, `_`) and makes the saved map the baseline; on the web it refuses and edits live in memory for the session (localStorage is the PRD's named follow-up). `EditorAction::Play` is the one thing `update` reports outward, and `Session` turns it into `play`. Tests: `editor_tests` (stroke and toggle-erase rules, singleton moves, settings/load/reset as undo steps, `update` from raw input, the bar slots, the hit slack, popups inside the field, the category button halves, wheel cycling, popup exclusivity) and `history_tests`. Two players: `Tool::Start2` (`"start2"`, ACTOR, label `p2 start`, singleton independent of `Start`, the tank icon over `draw_player2_ring`) makes `TOOLS` 24, and the MAP panel's `SettingsRow::Tank2` (`TANK 2`, `MapSettings::tank2`, `CliOverrides::tank2`) edits the map's `tank2` key.
- `game.rs` — the presentation layer: `Game::render` plus `Textures`/`Effects`. Reads `Game`'s state (owned by `simulation/`) and draws it; never mutates it. Takes a `&Layout`: pass 1 renders the field into `scene_target` at the field's own size, pass 2 blits it at the field origin (plus the camera shake) and draws everything field-relative - the flash quads, the debug overlays, the banners and the dim/flash rectangles - inside one `Camera2D` whose offset is that origin, so the simulation's screen-pixel positions are used as they are and a dim or a flash never covers the bar; the bar itself is drawn last, in window space, by `hud::draw_bar`. Also takes a `&hud::PlayChrome` (`Session::play_chrome`): `build_button` draws the `BUILD` mode button at the bar's right end after the bar, and `leave_dialog` dims the field like PAUSED and draws `hud::draw_leave_dialog` inside the field camera - window chrome, not simulation state (the round is frozen because `main.rs` is not calling `update`, see `mode.rs`).
- `hud.rs` *(presentation only)* — the HUD bar above the field (docs/hud-and-builder-layout-design.md, variant A): `HudModel::gather` pulls the readouts off `Game` once per frame as plain values, `draw_bar` lays them out as **fixed slots** (mission + wave, the live enemy count with a dim `+N` for the ones still to roll in, a pixel heart + HP, the shell sprite + count, three weapon slots of pickup icon + count with the live one outlined in its accent, `SPEED`/`SHIELD`/`FROG` bars) so a number changing width never nudges its neighbours; `hud_tests` pin the slots inside the default width without overlap. Text is 18 px (`HUD_TEXT_SIZE`, which the editor's bar shares); the bar is a plain dark strip one cell tall so the 32 px icons sit full-bleed. `hud_number_color` and the weapon accent colours live here. The right end of the bar is the **mode button** (`mode_button_rect`/`draw_mode_button`, `MODE_BUTTON_W` = 72 px, full bar height so a finger has the most to aim at): `BUILD` in play mode, `PLAY` in build mode, both in `BUILD_COLOR` (the builder's amber, which `editor/` re-exports as `BUILD_ACCENT`); one rect shared by the play bar, the build bar and every hit test, so a tool's `click` and a finger agree on it, and `hud_tests` pin that the readouts end before it. The **leave dialog** lives here too (`leave_dialog_rects`/`draw_leave_dialog`, field space: a centred `DIALOG_W` x `DIALOG_H` panel with `LEAVE ROUND`/`KEEP PLAYING` buttons of at least 160 x 48 px, 16 px apart, pinned by `the_leave_dialog_buttons_are_finger_sized_and_inside_the_field`), as does `PlayChrome` (`build_button`, `leave_dialog`) - the plain flags `Session::play_chrome` hands `Game::render`, so play-mode chrome stays in one file. `draw_debug_overlays` draws the debug overlays - the inspect hitbox/stat readout and the other layers (blocked nav cells, each enemy's waypoint/committed heading/last behaviour-tree action, projectile hit boxes, engagement targets, pickup radii) are all flags of `Game::debug_overlays` (`Overlays`, `inspect` included) - screen space, post-composite, gated per flag. The I key cycles the presets off -> inspect -> all (`Overlays::next_preset`), and a `DEV overlays: <preset>` label shows which preset is live. The drawing code is `#[cfg(feature = "dev-tools")]`, so release builds contain none of it and the key is inert there. **Two-player rounds** use a second fixed slot table (`SLOTS_TWO` vs `SLOTS_ONE`, both pinned by `hud_tests`): `HudModel` holds a `PlayerHud` per player (`p2: Option`, a wreck shows zeros), HP/shells/weapon counts draw as `draw_pair` (`60|70`, each side through `hud_number_color`), the live weapon is a `draw_pair_underlines` underline instead of the slot outline, and SPEED/SHIELD are two `BAR2_H` gauges stacked (`draw_gauge`). The **players button** (`players_button_rect`, 48 px left of the mode button, `draw_players_button`: one or two `draw_tank_glyph` tanks, the second in `tank::PLAYER2_RING_COLOR`) opens the **players dialog** (`players_dialog_rects`/`draw_players_dialog`, the leave dialog's geometry through the shared `two_button_dialog`/`draw_dialog_panel`/`draw_dialog_button`); `PlayChrome` gained `players_button`/`players_dialog`.
- `fx.rs` *(presentation only)* — the short-lived particle layer: `Particle`/`ParticleKind` (Spark, Chip, Dust, Smoke, Ember) and `Fx`, which `main.rs` owns and threads into `Game::render` through `Effects::fx`. **Deliberately not a field of `Game`**: nothing in `simulation/` can see it, no snapshot carries it and `render` takes `&Game`, so there is no path from a particle back into a simulation value - which is exactly why this module may use `rand::rng()` freely while `decal.rs` may not. The rule of thumb: anything whose *position matters* to gameplay later (where rubble lands) belongs in `decal.rs`; `fx.rs` is only for things that vanish. `Fx::observe` runs between `Game::update` and `Game::render` and has two halves - one-shot bursts diffed out of `game.events()` (guarded on `Game::frame()`, because the dev server renders many times without advancing and the event log still holds the last advanced frame), and continuous emitters sampled from `Game::burning_tiles`/`burning_wrecks`/`ramming_tiles`/`contacts` (the last driven by `Physics::contact_stats`, whose `max_impulse` and contact point had been computed every frame and read by nothing but the probe - so hitting a wall, shunting a wreck or grinding through a pileup produced no feedback at all) (states, not events - a tile burns for a second and a half, so there is nothing in the log to drive them from) rate-limited through a per-source fractional accumulator. Everything draws as a raylib primitive rather than a sprite, non-additive kinds in one run then all additive ones inside a single `BLEND_ADDITIVE` block, because a blend switch breaks the batch. **Particles are quantised to the same 2-screen-pixel block every sprite in the game lands on** (`FX_GRID`): positions snap to the grid, sizes are whole numbers of blocks, alpha steps in four levels, and fire/smoke step through a short hand-picked colour ramp instead of fading a channel - drawn at sub-pixel positions with smooth circles and continuous alpha they read as a different, softer game layered over this one. `blast.rs`'s `pixel_disc` does the same for the blast and fuse glows, which are the largest smooth shapes an explosion would otherwise put on screen. The one emitter whose source is neither on fire nor in contact is `Game::grass_disturbed` - the tall-grass cells a *moving* tank is crossing, which throws leaf specks. `fx_max_particles` caps it oldest-first; `fx_density` scales every count and `main.rs` halves it under `cfg!(target_os = "emscripten")`. Tests in `fx_tests` (cap, oldest-first eviction, the chip's fall/bounce, the rate limiter). The dev overlay label carries frame-time and the live particle count, which is how the "holds up on web" claim is actually checked.
- `frog.rs` — the frog entity (`Frog`, `Side` - Player or Enemy; the same struct serves both frogs, the Hunt mission's enemy frog is just `side: Enemy` with a red ground ring instead of white - `draw_frog_ring`, which draws that ring as the frog's health gauge, `RingStyle::Gauge` in the white ramp for the player's frog and the all-red ramp for the enemy's, always on while the frog lives): bite and evasive-hop reflexes driven from `simulation/`, health, animation. Any shot damages any frog, whoever fired.
- `tank.rs` — tank entity: state, movement, drawing. Also home to `TankKind`, the 12 chassis named in sprite-sheet row order (`tuning::TANK_NAMES`' order, locked in by `chassis_tests`) — the one list `--tank`, a map's `tank` key and the `player_tank` knob all spell a chassis from, deriving both the CLI's `ValueEnum` names and the map TOML's serde names so they can't drift apart. `despawn_timer`/`alpha()`/`tint()` fade a wreck out before a wave round removes it. Also home to the ground-ring **health gauge**: `RingStyle::Gauge` draws the ring's band as a donut from 12 o'clock clockwise for the remaining-health fraction (`Tank::health_fraction`, `health_ring_sweep`), coloured by `HealthRamp` (`White`: white, gold, bright red, deep red by quarter of health, `health_ring_step`; `Red`: the enemy frog's all-red ramp), the missing arc drawn in a dimmed base colour or, for enemies, a dark band. `draw_player_ring` (always on, the white marker dimmed to `health_ring_base_opacity` under the missing arc) and `draw_enemy_ring` (`enemy_health_ring_visibility`: on for `health_ring_hit_seconds` after a hit, fading over `health_ring_hit_fade_seconds`, and for good once at or under `enemy_health_ring_below`; gap at `health_ring_gap_opacity`) both yield to the shield ring through `shield_visibility`; `health_ring_tests` lock the rules in. `PLAYER2_RING_COLOR` (the palette's mid blue), `HealthRamp::Blue` and `draw_player2_ring` are player 2's marker; `Tank::owner`/`owner_slot()`/`is_player()` are the identity (see `simulation/`).
- `shell.rs` — projectile entity: state, movement, drawing. See docs/SHELLS_SPEC.md for the `shells.png` row/column layout and the per-tank variant tables in `lib.rs`. Also home to `Owner` (who fired something — shared by `Shell`, `bullet::Bullet`, plasma and the laser; `Tank::owner()`/`Owner::slot()` convert to and from `Tank::owner_slot`, and `Owner::same_side` is the friendly-fire test).
- `laser.rs` — the laser weapon's on-screen flash (`LaserBeam`/`LaserVariant`): a limited-charge, instant-hit weapon granted by `pickup::PickupKind::Laser`, resolved same-frame by `Game::resolve_lasers` (no travel time, no sprite — just a drawn line, unlike `Shell`/`Bullet`).
- `bullet.rs` — the minigun's individually-simulated projectile (`Bullet`/`BulletState`): mirrors `shell.rs`'s shape (position/velocity/state) but with a compact 3-state machine (Muzzle/Flying/Hit) instead of `Shell`'s 7, since a burst fires them far too rapidly in succession for an elaborate wind-up/impact sequence to read well. See docs/BULLETS_SPEC.md for the `minigun_bullets.png` layout.
- `plasma.rs` — the plasma cannon's projectile (`Plasma`/`PlasmaState`): a limited-ammo weapon granted by `pickup::PickupKind::Plasma` (`Tank::plasma_ammo`), fired the exact same way a shell is — straight down the barrel, a twin-barrel chassis firing one bolt per barrel a beat apart (`Tank::pending_plasma_shot` mirrors `Shell`'s `PendingShot`) — and sharing `ShellState`'s overall Fire/Flying/Hit choreography/timings (`Flying` alone spans a 4-frame baked breathing cycle, not one static frame — see `flying_col`), but dealing `PLASMA_DAMAGE_FACTOR` (24%) more damage and rendered as a glowing, pulsating orb (`draw_plasma`'s runtime sine-wave glow layered on top of the baked `static/plasma.png` sprite — see docs/PLASMA_SPEC.md) that bursts into a small electric/sci-fi splash on impact instead of a shell's smoke-and-fire blast. Comes in two `PlasmaVariant`s (Teal base, Purple rarer/harder-hitting — `PLASMA_PURPLE_PICKUP_CHANCE`/`PLASMA_PURPLE_DAMAGE_FACTOR`, same reroll-on-pickup mechanism as `laser::LaserVariant`), each its own baked sheet row (a runtime tint was tried and rejected — see docs/PLASMA_SPEC.md §4). Unlike `shell.rs`, that row is keyed by ammo variant, not shooter chassis (`bullet.rs`'s "shared art" convention), and a bolt never ricochets.
- `pickup.rs` — battlefield pickups (`Pickup`/`PickupKind`: Health, Ammo, Laser, Minigun, Plasma, SpeedUp, Shield): position + kind, no physics body, collected by pure proximity (see `simulation/mod.rs`'s pickup phase). Placed via fixed map slots (`map.rs`'s `CellObject::Pickup`), not randomly. `SpeedUp` is a timed stat buff rather than a weapon/ammo grant: it sets (not adds to) `Tank::speed_boost_timer` to `SPEED_BOOST_DURATION_SECONDS`, during which `Tank::effective_speed` is scaled by `SPEED_BOOST_MULTIPLIER` — collecting another one while already boosted refreshes the timer instead of stacking, so a tank is only ever under one speed boost at a time. `Shield` (the rainbow shield) is the same shape of timed buff: full heal (`Tank::damage = 0`) plus `Tank::shield_timer` set to `shield_duration_seconds`, during which `Tank::take_damage` — the **only** path that adds damage to a tank (shells, ram, explosions, frog bite all go through it) — is a no-op; hit flash/knockback/AI alert still fire so a blocked shot visibly lands. Drawn as a hue-cycling ring under the hull that is itself a gauge of the time left - `Tank::shield_charge`: the rainbow bands cover that fraction of the circle from 12 o'clock clockwise, the rest drawn as the tank's health ring draws its missing part, so the shield visibly runs down at the same radius - (`tank::draw_tank_shield`, one `RingStyle` of the shared `tank::draw_ground_ring` - the same ring is the player's always-on marker and health gauge via `draw_player_ring` - `RingStyle::Gauge`, see `tank.rs`; both sit at `Tank::ring_position`, a spring-damper follower of the hull with its own `ring_velocity` (`tank_ring_spring_hz`/`tank_ring_damping`, leashed to `tank_ring_max_trail_px`: hangs back when the tank sets off, trails further the faster it goes, glides in when it stops), and cross-fade so they never stack). It is the one pickup that is normally *not* slot-backed: `maybe_spawn_bonus_shield` rolls `shield_near_health_chance` every time a Health slot is spawned or respawned and drops a shield in a free neighbouring cell (`bonus_shield_cell`), so the respawn timer's "field is full" test counts only slot-backed pickups (`slot_backed_count`). Any tank, player included, also starts shielded with `spawn_shield_chance` odds (rolled in `Game::init`).
- `obstacle.rs` — static battlefield terrain: `Obstacle` is a wall built from one of four materials (`Material`: Brick, Iron, Wood, Glass, each with its own decay/rust/burn lifecycle, docs/WALLS_SPEC.md for the `walls_sheet.png` layout) **or one of the three destructible props** (`Sandbag`, `Barrel`, `Fence` - docs/sandbags-barrels-fences.md, art on `props_sheet.png` per docs/PROPS_SPEC.md, `Material::sheet` says which atlas) **or one of the two tree species** (`Tree` broadleaf, `Pine` conifer - docs/TREES_SPEC.md, art on `trees_sheet.png`). The rest of the code asks the material's predicates (`is_permanent` - Iron, the only one that shapes line of fire and the linter's breach grid; `blocks_sight` - false for sandbags/fences; `is_wall`/`is_prop`/`is_tree`; `pass_over_chance`/`deflect_chance`; `ram_seconds`; `flammable_chance`; `is_explosive`) rather than matching on variants, so the scattered `== Iron` checks are gone. **Trees are the one obstacle whose sprite is bigger than its cell**: 48px art on a 32px grid (`Obstacle::sprite_size` vs `size`), so a canopy overhangs its neighbours and a grove's crowns interlock instead of tiling. They are consequently excluded from seam-closing in *both* physics and the projectile hit test (`battlefield::tile_half_extent`, the one function both paths call), get no edge cap, and are drawn in `game.rs`'s vegetation pass - after the tanks, sorted back to front - rather than with the walls. They also catch fire the way Wood does (`flammable`/`tick_burn`, shared burn columns 4-6 and `wood_burn_seconds`), and a tank can shoulder one over by driving into it (`tree_ram_seconds`) - a rammed tree dies outright rather than taking the flammable fork, since otherwise driving through a wood leaves a trail of fires. **A tree's idle animation is colour, not motion**: `tree_col` cycles `TREE_SHIMMER_FRAMES` copies of each damage stage that differ only in where a few patches of leaf step one rung up the foliage ramp, at a phase hashed from the tree's position - an ambient *bend* was built first and rejected, because what reads as alive on a blade of grass reads as wrong on a trunk. The one time a tree's geometry moves is `tree_lean`, the bend away from a tank ramming it (`ram_timer`), which `tree_blit` applies as **eight horizontal bands each shifted by a whole 2px block** rather than as a rotation - grass rotates about its base and gets away with it because a tuft is a few thin blades, but rotating a solid crown resamples its whole interior every frame and the canopy visibly churns (measured against a static capture). Equal-shift bands coalesce, so an untouched tree costs a single quad. Props get `fuse` (a barrel armed by a neighbouring blast, inert and drawn lit until it pops) and `ram_timer` fields; `Obstacle::new` is the one constructor. Drawing takes `ObstacleTextures` (both atlases) and a `FenceAxis` the renderer picks per frame from fence neighbours (`fence_axis`). Wall tiles also get an **edge-cap overlay** drawn over them (`draw_obstacle_cap`, sheet rows 22-25): the lighting along whichever faces are exposed to open ground, so a run of tiles reads as one structure rather than a grid. An overlay rather than a base+damage sheet rewrite, because one row per material then composites with every damage stage and variant. `neighbour_mask` computes a full 8-bit mask (diagonals only counting when both adjacent orthogonals are set) and `BLOB_TILE: [u8; 256]` maps it to a column - every entry is currently 0..=15, i.e. the 4-bit set, and widening to the 47-tile blob is a sheet+table change with no other code moving. The mask is **cached on `Obstacle`** and refreshed only by `Game::refresh_edge_masks` on destruction, since wall layouts only ever lose tiles - unlike `fence_axis`, which rebuilds its neighbour set every frame inside `render`. `MATERIALS`/`MATERIAL_NAMES`/`wall_max_health` stay the four *wall* materials; props have scalar knobs in `group props`.
- `blast.rs` — the barrel blast's presentation: `BlastFx` (the 12-frame fireball on `static/barrel_explosion.png`, `blast_anim_fps`), `Scorch` (the decal row of the same sheet, kept for the round, `SCORCH_MAX`), `draw_blast`/`draw_blast_glow` (additive `BlendMode::BLEND_ADDITIVE` discs built from 2px blocks by `pixel_disc`, no shader - a smooth circle here is the biggest thing breaking the pixel look during an explosion)/`draw_fuse_glow`/`draw_scorch`. Cosmetic seeds are a hash of the position, never an RNG draw. `game.rs` draws scorches under obstacles, the fuse glow after them, the blasts last in pass 1, and a brief whole-screen flash in pass 2; the ripple/shake/impact quad ride the existing `Frame::shock`/`impact_flashes`.
- `decal.rs` — what a destroyed tile leaves on the ground: `Decal` (material, frozen rubble row/col, position, kept for the round, capped at `DECAL_MAX`, cleared by `Game::init`) and `draw_decal`. Art is the dedicated rubble block at the bottom of `walls_sheet.png` (`RUBBLE_ROW_BRICK`/`_WOOD`/`_WOOD_CHARRED`/`_GLASS`, rows 14-17, `RUBBLE_VARIANTS` = 8 columns each with coverage ramping sparse to dense - see docs/WALLS_SPEC.md); plus `RUBBLE_ROW_SANDBAG`/`_BARREL`/`_FENCE` at rows 18-20 - **the props' rubble lives on the walls sheet too**, since the rubble block is one contiguous thing and `props_sheet.png` has no spare columns, so `draw_decal` always samples `ObstacleTextures::walls` whatever died. `Material::rubble_row(charred)` maps a material onto a row and returns `None` only for Iron, which never dies. The variant, mirror and quarter-turn all come from `blast::seed_at`, a *salted* position hash, so one material has 8x8 apparent forms, a levelled wall never reads as a grid of clones, and - like `Scorch` - no RNG is drawn, so cosmetics cannot shift a seeded replay. Note `seed_at` ends in an avalanche mix: every position here is a multiple of 32, so the raw products have five zero low bits, which is exactly where `seed & 1` and `seed % N` look. Staged on `Frame::decals` by `props::obstacle_died` - the one funnel every tile death passes through - and drawn in `game.rs` pass 1 between the scorches and the obstacles. A `Decal` can also be *thrown*: `Decal::thrown` gives it an `origin` and an `arc`, and it flies from one to the other over `debris_flight_seconds` before settling - `flight`/`height`/`draw_pos` derive the whole trajectory from `age`, so nothing integrates it and a cosmetic arc can never move a landing spot the simulation already chose. `game.rs` draws landed decals early in pass 1 (under everything that stands) and airborne ones last of all with `draw_decal_shadow` beneath them, so a chunk of hull passes over tanks rather than under them. Row 21 (`RUBBLE_ROW_TANK`) is outside `Material::rubble_row` entirely - a tank is not an obstacle - and is named directly by `Game::wreck_fx`. `Decal::blocks` is an unread Phase-3 hook: rubble is cosmetic today, but *where it lands* is already decided in `simulation/`, so making it matter later changes only the consumers.
- `grass.rs` — tall grass: `GrassTuft`, `tufts_for_cell`, `draw_tuft`, and the `conceals` point query. **Deliberately not an `Obstacle`**: `Game::nav_grid` feeds every obstacle into pathfinding with no material filter and `maplint` reasons the same way, so anything that is one is unconditionally impassable to the AI and a wall to the linter - grass you drive through cannot be that. Modelled on `decal::Decal` instead: simulation-owned, seeded from `blast::seed_at` so it never draws round RNG, rebuilt only in `Game::init`. A map marks whole cells (`CellObject::TallGrass`); each scatters `grass_tufts_per_cell` tufts at hashed offsets, because the occlusion has to be *partial* - the reference hides a unit at worst ~44%, by walking between discrete tufts rather than into a solid block (measured here: 2 tufts/cell = 53% of a parked tank, 4 = 83%). **Drawn interleaved with the tanks and frogs, not after them**: `game.rs`'s back-to-front pass merges the tufts (pre-sorted by root in `Game::init`, since they never move) against the y-sorted units, so a tuft rooted *behind* a tank is drawn behind it. Drawing all grass last - which it used to - buries a tank in grass that grows well past it. Over the tanks in *front* is the entire hiding effect, since the reference uses nothing but draw order and never makes the unit transparent; under the projectiles so you can still see your own shots leave the grass. Trees are the deliberate exception and still draw after the lot: a crown is above tank height, so it overhangs a hull on either side of the trunk - you drive *under* a tree and *through* grass. Sway is a CPU sine of `Game::time` plus a per-tuft hashed phase, applied as a rotation about the tuft's base so the tip moves and the root stays put; there is no shader, because each one needs a hand-ported GLSL ES 100 twin. A tank driving through carries two more per-tuft values that `Game::tick_grass` ticks (a simulation phase so the timing is frame-rate independent, but cosmetic - no RNG, replays unaffected): `crush`, driven to 1 under the hull *box* (not a radius from its centre, which leaves the grass under the tracks standing) and recovered over `grass_crush_recover_seconds`, which is the whole trail effect and is also why the wake needs no direction-of-travel geometry; and `push`, the sideways shove, stronger ahead of a moving tank than behind so a hull drives a bow wave. `fx.rs` samples `Game::grass_disturbed` for the leaf specks a hull kicks up. All three are *our* additions - the reference gif sways ambiently and does not react to the unit at all. **Concealment**: `Terrain::conceals` is a point query against the grass *cells* (not the drawn tufts - cover is a property of the ground, and testing sprites would make hiding depend on which way the wind blew), and `enemy_phase` gates `player_line_of_sight` on it. That stops enemies *firing* at a hidden player and nothing else: the group alert (`any_enemy_sees_player`) is a pure distance test with **no line-of-sight check at all**, so "nobody can see the player" is not a state this AI can reach - enemies still converge and will ram. Gating that too is what would make concealment read fully and is also what re-opens the pile-up behaviour the engagement ring was tuned to solve, so it is deliberately out of scope; do not add it without re-baselining `just probe-fixtures`. Note `line_of_fire_to_frog` filters on `is_permanent`, not `blocks_sight`, so a hunter aiming at the frog is unaffected by grass - correct, since it is not shooting the player. **Concealment gates four things**, and it has to be all four: the shared alert (`any_enemy_sees_player`), the attack and chase tiers in `ai::build`, and ram damage in `sync_tanks_and_ram`. Gating only the shot was measured and left the pack standing on top of a player it could not see - `act_attack`'s unaligned branch repositions *toward* the target, so an enemy that cannot fire still closes - and the ramming that replaced the gunfire cost more health than the gunfire had. The one exemption is `Ai::is_hit_alerted`: a tank the player shot comes looking anyway, which is the whole cost of the mechanic - cover hides you until you use it. A *range*-based reveal was tried instead and measured worse than no concealment at all: revealing at 96 px handed enemies point-blank shots that never miss.
- `ground.rs` — the decorative grass/dirt/road floor layer, built once per round by `Game::init` and drawn first in `render`, before everything else. No physics, no gameplay effect. Carries two shading cues (docs/GROUND_SPEC.md §4): **wall ambient occlusion** as a per-cell tint baked into `GroundGrid::tints` at build time (so it costs no extra draw calls, and it can be a flat per-cell tint only because its steps land on the wall grid and read as a shadow edge), and the **screen-edge vignette** as four per-pixel gradient bands in `draw_edge_shade` - that one *cannot* be a cell tint, because a flat tint over a 32px cell stair-steps visibly on flat-coloured grass wherever there is no wall for the steps to align with. Sourced from the third-party Puny World tileset (`static/punyworld/` - see docs/GROUND_SPEC.md and static/punyworld/SOURCE.md) using that pack's own pre-built Tiled autotile data rather than a hand-rolled one. This tileset's own colours are also the source of `tools/punypalette.py`, the shared palette every other generated sheet now draws from - see the Asset pipeline section below.
- `physics.rs` — rapier2d wrapper (`Physics`): solid bodies only (tank movement colliders, walls, obstacles, the frog), impulses, contact read-back, the fixed-timestep step. `settle_wreck` is the one place damping is ever set: rapier defaults to none and a wreck keeps its full-mass dynamic body while no longer being driven, so a shoved hulk used to slide until something stopped it - it is applied on the single frame a tank becomes a wreck (`roll_wreck_col` returns true there), because a wreck is made by damage mid-round rather than spawned, so `RigidBodyBuilder`'s damping is unavailable. No sensors or collision groups any more - projectile hits are pure geometry in `simulation/hits.rs`. `Physics::quarantined` reports rapier's own NaN quarantine (bodies/colliders it rolled back and disabled because their state went non-finite) after each step; `step_world` turns a non-empty report into `Event::PhysicsQuarantine`, which is a solver blow-up and never normal play. See docs/physics-engine-design.md ("Projectile hit testing").
- `track.rs` — tank tread marks left on the ground. A mark a tank died on top of is `scorched`: darker, and it never fades, so the kill site stays legible for the rest of the round even after a wave clears the wreck away (`Game::scorch_tracks`, `wreck_track_marks`/`wreck_track_darken`).
- `damage_stage.rs` — escalating damage overlay drawn on top of a tank.
- `ai.rs` — enemy decision-making (`Intent`, targeting, firing); builds and ticks behavior trees from `bt.rs`. `Ai::steer` routes its naive straight-line heading through `pathfind::Grid` before applying direction commitment/predictive-dodge, so obstacles are just another reason the heading bends. Two safety nets on top of that routing, both added after denser obstacle layouts started producing stuck tanks: (1) an obstacle-ahead override in `steer` bypasses the normal `AI_DIR_HOLD_SECONDS`/`AI_DIR_SWITCH_MARGIN_PX` commitment gate (debounced by the much shorter `AI_OBSTACLE_OVERRIDE_HOLD_SECONDS`, so it doesn't itself reintroduce jitter) whenever the committed heading is about to walk into a grid cell `pathfind::Grid::blocked_ahead` already knows is blocked; (2) a stuck-escape (`Ai`'s `last_position`/`progress_avg`/`stuck_timer` fields, `stuck_speed_eps`/`stuck_escape_seconds`/`stuck_progress_window_seconds`) catches everything (1) can't, including a genuine no-path layout - `think` measures the tank's own *displacement* since the previous tick (never a physics velocity: the contact solver hands a tank pressed against another body a velocity along its heading every frame without it going anywhere, which is how two enemies once sat jammed corner to corner in a corridor for good), projects it onto the heading it commanded last tick so it can tell "commanded to move" apart from "actually got somewhere that way" - a tank carried sideways by a jam of other tanks counts as stuck even at full speed - and smooths it over `stuck_progress_window_seconds` so a one-frame shove cannot clear the clock (`ai.rs`'s `stuck_tests`; `mechanics_tests::two_enemies_jammed_corner_to_corner_in_a_corridor_break_free` is the jam). (3) **breach**: a tank that keeps commanding movement into a destructible tile (`Terrain::obstacle_ahead` per direction, passed into `think` as `walls_ahead`; `Ai::wall_ahead_timer`) for `enemy_breach_after_seconds` stops, faces the tile and shoots it down (`Brain::wants_breach`/`act_breach`, a tier between flee and retreat) - only while healthy and stocked (`enemy_breach_max_damage`, `enemy_breach_min_shells`), never iron, waiting out a burning wood tile rather than wasting shells on it, and giving up after `enemy_breach_give_up_seconds`; locked in by `mechanics_tests::a_walled_in_enemy_shoots_its_way_out`. (4) **personal space**: `crowded_ahead` + `Ai::yield_timer`, applied once at the end of `think` to whatever the tree decided rather than inside each behaviour, since attack, chase, patrol, wander, hunter and guard all converge on the same places and slammed the same way. A tank with something inside `enemy_separation_px` (hull surface to hull surface) *directly ahead* - in the lane, by perpendicular distance, and in front, by the sign of the dot product, so a tank merely passing does not brake - drops `move_dir` and keeps `face`, so it pulls up short while still aiming and shooting. This is deliberately a **brake, not another sidestep**: `avoid_collisions` already dodges paths that will cross and explicitly stops caring once two tanks are inside `avoid_margin`, which is exactly the regime that produced the slam. `enemy_yield_seconds` is a hard ceiling on the hold, and it is load-bearing: the stuck escape counts only tanks that were *commanded* to move, so two tanks nose to nose would both brake and neither would ever move again. Past the ceiling the brake releases and behaviour is what it was, making the worst case a visible pause rather than a freeze. Measured on a bare map with the player parked, over 8 seeds: enemy-vs-enemy rams 36 -> 16, rams into the player 17 -> **0**, total ram damage 204 -> 67, with the enemies' near-stationary frame share slightly *down* - they are not queueing, they are arriving unbunched. Stop early and dwell briefly beats stop late and long: a narrow gap with a long hold queued tanks nose to tail in the maze fixture's corridors and tripped its clustering ceiling. `ai::separation_tests` locks the ram counts in. `AiSnapshot` (`Ai::snapshot`) is the whole memory as plain values, including an `escapes` counter the stuck escape bumps so tooling can see an escape that fired and reset within one frame, and `yield_timer`. **Roles** (`ai::Role`, `Ai::role`, rolled last in `roll_role` when a tank joins the fight so a zero share draws no RNG): `Player` is the default behaviour (target = the player); a `Hunter` (Protect: `enemy_hunter_share_protect`, Hunt: `enemy_hunter_share_hunt`) drives at the player's frog from anywhere as an objective, competes for slots on the second ring `Game::engage_frog` (built even for a lone hunter when it has no route to the frog's own cell - a bunker, a plugged corridor), gates fire on the line of *fire* to the frog (`Terrain::line_of_fire_to_frog`: only iron and other frogs obstruct, so it shoots destructible bunker walls down on the way), only snipes the player when already lined up in range and then not again for `hunter_snipe_cooldown_seconds`, fights the player instead while it has no direct route and no tenable slot, and falls back to `Player` for good once that frog is dead; a `Guard` (Hunt only) holds an annulus around its own frog (`guard_leash_px` outside, `guard_keep_off_px` inside so it stays out of the bite/hop range) and engages the player only inside the leash. `Ai::think` takes `target`/`frog_target` positions and `player_line_of_sight` - still snapshot-only.
- `bt.rs` — small generic, game-agnostic behavior-tree engine (Selector/Sequence/Condition/Action) used by `ai.rs`. `Action` leaves carry a name and `tick_traced` reports the last one that ran, which is how `Ai::snapshot()`'s `last_action` (and the `ai` overlay's label) knows what the tree decided.
- `pathfind.rs` — small grid-based A* (`Grid`) so AI routes around static obstacles; game-agnostic like `bt.rs`. Rebuilt fresh each frame in `simulation.rs` from the current obstacle layout, per the AI-decoupling principle in docs/physics-engine-design.md (AI reasons over snapshots, never the ECS/physics world directly). Has its own `#[cfg(test)]` unit tests (the one algorithmic, non-visual piece of the codebase) — run with `cargo test --lib pathfind`.
- `shockwave.rs` — `Shockwave` (center, age and a per-event `strength`, with `remaining()` = strength faded by age) plus `RippleFx`/`RippleTuning`, the post-processing ripple-shader driver for the GLSL shaders in `static/*.fs` (shockwave, muzzle flash, impact). `Game::shocks` is a **list** capped at `SHOCK_MAX` (`lib.rs` - it is the shader's uniform-array length, i.e. layout, not a feel knob): a chained barrel cascade sets off one ripple per link, and the old single last-write-wins slot meant the tank explosion that started it simply vanished. They resolve in **one blit** - `static/shockwave.fs` accumulates every live ripple's displacement and samples the scene exactly once, because N passes would re-distort the previous pass's output and cost N full-screen samples. Overflow evicts by `remaining()`, not by age, so weak cook-off pops cannot shove out a real kill. Relative strengths live in `simulation/mod.rs` as `SHOCK_KILL`/`SHOCK_BARREL`/`SHOCK_FROG`/`SHOCK_COOKOFF` (ratios between events; the overall amount stays a tuning knob, and `screen_fx_intensity` scales the three whole-screen effects - kill flash, ripple bend, camera shake - together, so a reduced-flash mode is one slider while the local fireball, glow, impact quad and particles stay put). Camera shake sums the live ripples, phases each off its position hash so they interfere rather than beat in lockstep, clamps the total at `camera_shake_max_stack`, and **snaps to whole 2px blocks** - the offset moves the whole composited scene, so a fractional value makes every pixel in the game sample between texels for the duration of the shake.

## Asset pipeline (generated, not hand-drawn)
- The three sheets `main.rs` actually loads for tanks/shells/walls — `static/scifi_tanks_sheet.png`, `static/shells.png` (18 variants), `static/walls_sheet.png` — are all procedurally generated by the Pillow-based scripts in `tools/spritegen/` (`gen_tanks.py`, `gen_shells.py`, `gen_walls.py`; one file per sheet, deterministic fixed seeds). Regenerate in place with e.g. `SPRITE_OUT=static python3 tools/spritegen/gen_tanks.py` — default `SPRITE_OUT` is `assets/sprites`, so the env var is required to write into `static/` where the game reads from (it also writes ~150 individual per-tank debug PNGs alongside the sheet - `main.rs` never loads these, only the combined sheet, so delete them after regenerating rather than leaving them in `static/`). Requires Pillow, not currently declared in `devenv.nix`. **Plain `pip3 install pillow` / `python3 -m pip install pillow` do NOT work here** - the nix-provided `python3` has no `pip` module at all (nix expects packages added via nix, not pip) - use `nix-shell -p "python3.withPackages (ps: [ps.pillow])" --run "SPRITE_OUT=static python3 tools/spritegen/gen_tanks.py"` instead (or add `pillow` to `devenv.nix`'s `languages.python`/`pkgs.python3.withPackages` for a persistent fix).
  Specs, one per sheet: `docs/SPRITESHEET_SPEC.md` (tanks), `docs/SHELLS_SPEC.md` (shells), `docs/WALLS_SPEC.md` (walls), `docs/BULLETS_SPEC.md` (minigun bullets), `docs/PLASMA_SPEC.md` (plasma bolts) — all self-contained (column/row maps, pivots, palettes), no need to open the PNGs to slice or edit them correctly.
- The minigun's two Pillow-generated assets follow the exact same `tools/spritegen/` convention as tanks/shells/walls: `tools/spritegen/gen_bullets.py` → `static/minigun_bullets.png` (the bullet sheet, see docs/BULLETS_SPEC.md) and `tools/spritegen/gen_minigun_mount.py` → `static/minigun_mount.png` (a 3-frame turret-mounted barrel-cluster overlay drawn by `tank::draw_minigun_mount`, one "hot barrel" per frame, cycled while firing rather than rotated — this is a top-down game, so a barrel cluster's real rotation axis points along the ground plane, edge-on to the camera, and spinning the sprite in the screen plane would read as a helicopter rotor seen from above; see docs/SPRITESHEET_SPEC.md's composition-order section and the generator script's own doc comment).
- The props' two generated assets follow the same conventions: `tools/spritegen/gen_props.py` → `static/props_sheet.png` (128x288, sandbags/barrels/fences; each cell drawn on a 16px macro canvas and upscaled 2x NEAREST, which is pixel-identical to walls' `pixelate()` - do not pixelate it again) and `tools/spritegen/gen_barrel_explosion.py` → `static/barrel_explosion.png` (768x128: 12 x 64px blast frames drawn at scale 2 like the frog filmstrips, plus 3 scorch decals). Spec: docs/PROPS_SPEC.md. Verify with the PALETTE.md off-palette check (both must print 0) and that explosion frame 0 is non-empty.
- The plasma cannon's two generated assets follow the same conventions already established above: `tools/spritegen/gen_plasma.py` → `static/plasma.png` (the 7-column bolt/burst sheet, Pillow-based like `gen_shells.py`/`gen_bullets.py` — see docs/PLASMA_SPEC.md) and `tools/gen_plasma_pickup.py` → `static/pickups/plasma.png` (the ground pickup icon, raw PNG bytes, no Pillow — same convention as `gen_laser_pickup.py`/`gen_minigun_pickup.py` below).
- **Every generated sheet's colours come from one shared palette** (`tools/punypalette.py`, a curated set sampled directly from the third-party Puny World ground-layer tileset; `gen_walls.py` alone uses `PUNY_PALETTE_ALL`, the base set plus eight interpolated in-between steps - Puny World is a 16px-prop tileset whose ramps can tint a barrel but not *shade* masonry, and the greys are the thinnest, with a 71-value cliff from `STONE_DK` to `STONE_DARKEST` that `inner_shadow` used to jump straight across. The extension is additive and opt-in because `snap()` is called by every generator - regenerating tanks/shells/props produces byte-identical files, and `just check-sheets` enforces that an extended colour anywhere but the walls sheet is a failure) — see `docs/PALETTE.md` for the why/how, the pixel-level verification method, and why this replaced an earlier pass built on the generic Resurrect 64 palette (`tools/resurrect64.py`, kept only as historical reference - nothing imports it anymore). All generators (`gen_tanks.py`, `gen_shells.py`, `gen_walls.py`, `gen_damage.py`, `gen_bullets.py`, `gen_minigun_mount.py`, `gen_plasma.py`, `gen_props.py`, `gen_barrel_explosion.py`) import `punypalette`; any new sprite work should too rather than introducing a fresh literal colour.
- **Pickup icons (`static/pickups/*.png`) are a separate, smaller pipeline from the sheets above** — one standalone 32x32 PNG per kind, deliberately *not* palette-snapped (loud/high-contrast, so a pickup reads at a glance against muted terrain - see `static/pickups/SOURCE.md`). `health.png`/`ammo.png` are copied unmodified from a third-party pack; `laser.png`/`minigun.png`/`plasma.png`/`speedup.png` are generated from scratch by `tools/gen_laser_pickup.py`/`tools/gen_minigun_pickup.py`/`tools/gen_plasma_pickup.py`/`tools/gen_speedup_pickup.py` (and `shield.png` by `tools/gen_shield_pickup.py`, which instead reads `health.png` and sweeps its red through the rainbow so the shield reads as a rainbow health pack), which write raw PNG bytes directly (no Pillow), same convention as `tools/gen_damage.py`.
- `static/damage.png` is generated by `tools/gen_damage.py`, which writes PNG bytes directly (no Pillow dependency). `static/tracks.png` is a small hand-authored/static asset with no generator script — its one dark-earth tone was recolored onto the palette with a one-off pixel remap rather than a persisted tool, since there's nothing else to regenerate.
- **`tools/gen_shells.py` (the old, no-Pillow, hand-rolled-PNG-writer script) is stale** — it still emits a 3-variant, 224×96 `shells.png`, superseded by `tools/spritegen/gen_shells.py`'s 18-variant, 224×576 sheet that's actually in `static/` and wired up (`SHELL_VARIANTS = 18` in `lib.rs`). Do not run the old script — it would regress the live sheet back to 3 variants. Kept around only as the generator for reference/history; not part of the live pipeline.
- `static/tanks.png`, `static/tanks_turret.png`, `static/tanks_candy.png` (an earlier tank-art iteration `main.rs` no longer loads, plus a recolor preview generated from it) and `static/walls_sheet_light.png` (an unreferenced walls-sheet variant, never wired into `main.rs`) were deleted as unused - confirmed via `main.rs`'s `load_texture` calls (`scifi_tanks_sheet.png`/`shells.png`/`damage.png`/`tracks.png`/`walls_sheet.png`, later joined by `props_sheet.png`/`barrel_explosion.png` and the rest, all literal paths, nothing dynamic) being the only textures the game ever loads. `tools/analyze_turrets.py` and `tools/gen_tanks_candy.py` read the now-deleted `static/tanks.png` and will error if run - left in place as historical reference (same convention as the stale `tools/gen_shells.py` above) rather than deleted, since removing tools wasn't asked for.
- `tools/spritegen/gen_grass.py` -> `static/nature_sheet.png` (tall grass, 3 species x 8 variants at 32px, drawn at `grass_scale` 2.0). **The one sheet authored at one design pixel per *sheet* pixel**, not on the walls sheet's 2px block grid: it is drawn at 2.0, so a sheet pixel is already a 2x2 screen block, and stacking a 2px grid on top of that made grass twice as chunky as everything around it (it was, until the trees landed beside it). Blades are two sheet pixels wide at the base and taper to one at the tip. Authored at 32px rather than the ground's 16 because a tuft has to reach a good part of a tank's 64px height to occlude it. Drawn from scratch on the Puny Palette rather than lifted from the reference pack (ninjikin's GRASS+), whose 37 colours are **100% off this palette** - hue ~100 swinging to teal 174 in shadow against Puny World's yellow-green - so its pixels would read as a different game. **This is the one sheet exempt from the no-green rule** in `just check-sheets`: the rule means "manufactured objects are never green; vegetation is", and grass that cannot be green is not grass. It also uses `GREEN_SHADE`, an interpolated step added to `PUNY_EXTRA` because `GREEN_DARKEST` to `GREEN_DK` is a 70-value jump with nothing between - blades built without it read as a solid dark block with light specks floating over it. Note the base green must be *darker* than the field: `GREEN_DK` matches the retinted live ground almost exactly, and blades drawn in it are invisible.
- `tools/spritegen/gen_trees.py` -> `static/trees_sheet.png` (the two tree species, 4 variants each, 3 damage stages + a 3-frame burn loop, plus two rubble rows). **48px cells, the only obstacle art that is not 32**, and the only sheet with an animation frame axis on top of its damage stages (`col = dapple frame * 3 + stage`) - see docs/TREES_SPEC.md 1 for why that keeps the "one design pixel is two screen pixels" invariant rather than breaking it: the cell grew because a tree is bigger than a wall tile, the pixels did not. Green is allowed here for the same reason it is on `nature_sheet.png`. It draws into a design-pixel buffer and expands to 2x2 blocks at the end, so unlike `gen_walls.py` there is no `pixelate()` pass - the block grid holds by construction.
- To change a live sprite, edit the relevant `tools/spritegen/*.py` (or `gen_damage.py`) generator and rerun it — don't hand-edit the PNGs. Then run **`just check-sheets`** (`tools/check_sheets.py`): it asserts every generated sheet is fully on the Puny Palette, and that the three sheets drawn *over* the ground layer (walls, props, barrel_explosion) contain no green at all — a green pixel there reads as terrain showing through, which is the olive look the de-green pass exists to prevent. The check is deliberately scoped: a green tank chassis is a real colour choice, and `plasma.png` is deliberately off-palette. It has already caught one: darkening a sand tone with `mul()` snapped it into the green family, because `snap()` is nearest-Euclidean over the whole 41-colour set — **shade with an explicit adjacent palette step, never a computed multiple**.
- **`walls_sheet.png` is authored on a 2px block grid so it reads at the same density as tanks.** Tanks draw their 32x32 source tile at `Tank::scale = 2.0` (`tank.rs`), so each source pixel covers a 2x2 on-screen block; obstacles draw their own 32x32 tile at `OBSTACLE_SCALE = 1.0` (`lib.rs`), 1:1. Bumping `OBSTACLE_SCALE` isn't viable (it would double obstacles' on-screen size and break `OBSTACLE_GRID_SIZE`/pathfinding-cell/collider alignment, which all assume `Obstacle::size() == OBSTACLE_TEXTURE_SIZE`), so the 2x chunkiness is baked into the art instead - **every tile therefore has 16x16 effective design pixels, and that is the budget to design against**. `gen_walls.py` enforces it at the source: `px()` writes a whole `GRID`x`GRID` block and every other primitive routes through it, so the `pixelate()` pass at the end is a no-op that merely confirms the invariant. It used to be the opposite - the sheet was drawn at full 32px and *then* NEAREST-downsampled, which kept one pixel in four and silently ate ~75% of every 1px detail (mortar ticks, rivet highlights, plank edges, and 100% of the glass cracks), with survival decided by nothing but coordinate parity. Consequences of the fix: geometry must put a feature and its neighbour in *different* blocks to keep both (brick's bond was rescaled from a 4px to an 8px course for exactly this - a 3px face plus a 1px seam landed in one block and the bond collapsed into flat banding), and scatter counts/odds authored against the old loss are rescaled by `SPECK_SCALE`. `gen_props.py` reaches the same density the other way round, drawing each cell at 16 and upscaling 2x per cell - do not pixelate it again. Sheet dimensions, tile size and the column/row layout are unchanged; backups of the previous look live in `static/_backup/`.
- Before a sweeping recolor/art pass, back up the current sheets and the generator source that produced them into `static/_backup/<label>-<timestamp>/` and `tools/spritegen/_backup/<label>-<timestamp>/` (plain file copies, not tracked specially) so the previous look stays around to compare against or revert to. See `docs/PALETTE.md` for every past pass's backups (pre-Resurrect64 originals, two R64 sub-passes, now Puny Palette) as an example of the convention.
- **The ground/terrain layer (grass/dirt/road) is the one exception to "generated, not hand-drawn."** `static/punyworld/punyworld-overworld-tileset.png` is third-party art (see `static/punyworld/SOURCE.md`), not a `tools/spritegen/` output. Everything *else* was recolored to match *it* (`tools/punypalette.py` - see `docs/PALETTE.md`), not the other way around: once the ground layer actually shipped, the tanks/walls/shells' previous Resurrect-64-vivid colours read as neon plastic next to Puny World's much softer terrain. `ground.rs` builds the per-round layout and draws it; full design + the Wang autotile tables it uses (extracted from the pack's own Tiled `.tsx`) are in `docs/GROUND_SPEC.md`. An earlier from-scratch procedural version (`tools/spritegen/gen_ground.py`) was superseded before ever being wired in - kept only as historical reference, not part of the live pipeline.
  - **The live tileset PNG is a retinted copy, not the pristine pack art.** The pack's own grass is yellow-green and its dirt paths bright yellow-khaki, which made the whole battlefield read yellow/green (user feedback, 2026-08). `tools/retint_ground.py` applies a smooth hue-based HSV curve (grass hue-shifted toward the pack's own deeper tree-green, dirt muted toward earth-tan; wood/red/teal/water untouched) — it always reads the pristine original kept at `static/punyworld/_original/punyworld-overworld-tileset.png` and writes the live path, so it's idempotent; tweak its `CURVE` control points and rerun to iterate. Never edit the live PNG directly, and never overwrite `_original/`. Relatedly, `battlefield.rs`'s `FORTRESS_ROAD_SURROUND` is now 0 (was 1): the dirt ring around the "BONG!" glyphs visually merged into one giant khaki moat — see that constant's doc comment.

## Conventions
- **Comments describe the code as it is now, not its history.** Say what a thing does and why the rule exists; leave "used to", "before X existed", which probe sweep found what, and cross-references to deleted code out - git and `docs/` hold the history. A doc comment that narrates past versions is the main way this codebase's comments drifted from its code (a 2026-09 review of `simulation.rs` found a third of the file was comments, several describing behaviour that no longer existed). Also: consecutive `///` lines merge into one doc, so a blank line must separate one item's doc from the next item's.
- Tank/shell rotation `0.0` = facing up.
- **A new gameplay/feel number is a `tunables!` row in `tuning.rs`, not a `pub const` in `lib.rs`** (which is layout only now - see the module map). Read it via `tuning().name`; never write the global outside `tuning.rs`'s staging path; never `const X = tuning().y` (not const-evaluable - make it a fn) and never recover a direction by dividing by a speed knob that may have changed since the projectile spawned.
- Movement is **4-direction with momentum**: pressing a direction snaps the hull to face it and *accelerates* toward a fixed top speed; releasing decelerates on a curve rather than stopping dead. `Tank::control` only sets a commanded target - `Game::drive_tank` is the whole locomotion model (`tank_accel_force` when speeding up, an exponential `tank_decel_curve_rate` with a `tank_decel_snap_px` snap when slowing, and `tank_turn_grip_force` scrubbing lateral velocity every frame), applied as one impulse per frame. Note the distinction when reading combat code: `Tank::velocity` is the *commanded* cardinal vector, not what the body is doing - use `Physics::velocity` for that (see `combat::ram`).
- Sprite-sheet layouts, damage-stage frame groupings, and speed/damage tuning curves are documented as comments in `lib.rs` next to their constants — check there first.
- **Seeded-replay determinism on the simulation path** (docs/gameplay-verification-design.md): all round randomness flows from `Game`'s one seeded `SmallRng` stream — never call `rand::rng()` on the simulation path (the only allowed uses are the *seed draws themselves* — `Game::init`'s entropy fallback and the probe's base-seed draw — plus the editor's cosmetic `ground_seed`), and never iterate a `HashMap`/`HashSet` where the loop body consumes RNG, spawns entities, or breaks ties — sort first (see `MapFile::iter_cells`, which sorts for exactly this reason). `simulation/mod.rs`'s `determinism_tests` catches violations.
- `shells.png` has row-variants (`SHELL_VARIANTS`), matched to chassis via `TANK_SHELL_VARIANT_BY_ROW`/`TANK_SHELL_VARIANT_STAGGERED_BY_ROW` (barrel count, size class, accent colour) rather than rolled randomly. `Tank::shell_variant` is set at spawn and re-set on every shot the tank fires, alternating between the two tables via `Tank::alternate_shot` — a no-op for single-barrel chassis, whose two table entries are identical. The flying frame (col 3) is pixel-identical across all rows by design — only the fire/hit frames differ — so a shell looks the same in flight no matter which tank fired it.

- **`src/bin/probe.rs` — headless gameplay/mechanics probe.** Drives `simulation::Game` frame-by-frame with a scripted `Input` sequence and no window/renderer, then dumps tank state (position, velocity, rotation, damage, ammo, wreck) as text. Use this as the default way to verify or explore gameplay mechanics — movement, damage exchange, AI behavior, round outcome — since it's fast (no GPU/window) and its output can be read directly instead of eyeballing screenshots. Run with `cargo run --bin probe -- --scenario <afk|advance|brake|circle> [--enemies N] [--tank <chassis>] [--mission protect|hunt|destroy] [--spawn band|waves --waves N --wave-size N --wave-growth N --tier-start T --tier-end T] [--frames N] [--log-every N] [--seed S] [-m <map.toml>] [--json-out F] [--budget kind=N ...] [--heatmap]`; `--help` lists current options and each scenario's own doc comment. `-m`/`--map` picks the battlefield (same semantics as the game binary; default: the embedded `maps/default.toml`, so a bare probe run exercises the battlefield the game actually ships with — there's no more random/dense-obstacle stress-test flag, `--obstacles` went with the procedural generator; see `battlefield.rs`'s module map entry). **`maps/test/` is an adversarial fixture corpus** for exactly this flag — six hand-built layouts, one per known stuck/scrape failure class (u-trap, choke, tight-corridors, frog-block, maze, pockets), plus `props.toml`, the sandbag/barrel/fence playground (swept and linted like the rest, not adversarial), each with an explicit `Start`+`Frog` cell and a `tanks` count so runs are comparable; per-fixture intent, design constraints (the k≥6 corridor-clearance rule, spawn-band envelope, keep a route outside `BORDER_MARGIN`) and seeded baselines live in docs/gameplay-verification-design.md §2.2 and each file's own header comments (which an editor re-save would drop — edit fixtures by hand). Built on `Game::outcome()`/`Game::tank_snapshots()` (simulation.rs), the small public read-only accessors added alongside the probe for exactly this purpose — extend those, not raw `world`/`Entity` access, if a scenario needs more state (a probe binary is a separate crate from the library, so it only sees `pub` API, not `simulation.rs`'s `pub(crate)` internals). Add new scenarios by extending the `Scenario` enum and `input_for_frame` in `probe.rs`. **Two players:** `--players 2`, `--tank2`, `--p2-scenario` (default: the main scenario) drive player 2; anomaly checks measure each enemy against the nearest live player (what the AI targets); labels are `PLAYER1`/`PLAYER2` in a two-player round (`PLAYER` otherwise) and enemies `ENEMY#k` from `Game::first_enemy_slot`; the JSON record carries `players`.
  - Limitation: covers logic only (movement/damage/AI/outcome), not rendering, shader effects, or "feel" — for that, use the `run` skill against the real windowed game.
  - **Fully reproducible given a seed** (Phase 1 of docs/gameplay-verification-design.md): a round's entire RNG lives in one `SmallRng` stream seeded in `Game::init` (`Game::seed_override`/`round_seed()`; `update` takes it into a local and restores it at its end — no early return may sit between, a `debug_assert` at update's top catches violations). Both binaries take `--seed` (decimal or 0x-hex, `parse_seed` in lib.rs): the probe replays a round bit-for-bit; the game binary reproduces the same round setup and replays it identically on every R-key/auto restart (windowed *evolution* diverges over time under variable frame dt — probe↔probe is the bit-exact pair). A probe sweep derives round i's seed as base+i, prints the base in its header and each round's own seed in every `ANOMALY`/flagged-round line plus an end-of-sweep replay recap, and unseeded runs draw-and-print a base — so every run ever made is replayable. Guarded by `simulation.rs`'s `determinism_tests` (two seeds, 600 frames, run twice, bit-compared). Promote a nailed-down `(seed, scenario)` finding to a `#[cfg(test)]` in `simulation.rs` asserting the *behavioral* claim (not exact trajectories — RNG streams may shift across toolchain bumps) once it's worth locking in as a regression check.
  - **Capturing gameplay anomalies (stale/stuck/jittering tanks).** `probe.rs` also runs standing per-frame anomaly checks (`AnomalyTracker`/`check_anomalies`) against every enemy tank — scoped to enemies only, since the player's behavior is fully explained by the scripted `Scenario` already. Silent unless something trips; a hit prints one greppable `ANOMALY round=.. seed=0x.. frame=.. t=..s kind=.. tank=.. pos=(..) <detail>` line instead of requiring a full frame trace to be read — the `seed` makes every single anomaly line a self-contained replay recipe (paste into `--seed`). Twelve kinds so far, all tuned against real constants (`lib.rs`/`simulation.rs`) rather than guessed thresholds: `stale-start` (never got more than a few px from spawn at any point in the first 2s - judged on the farthest it got, so a tank that drove off and wandered back through spawn is not stale), `stall` (near-zero speed for 3s+ mid-round), `border-stuck` (parked within 40px of a battlefield wall — walls' inner faces sit exactly at 0/width/0/height, see `spawn_walls`), `jitter` (heading flip-flops A→B→A repeatedly within 2s — the exact failure mode `committed_dir`/`dir_hold` in `ai.rs` exist to prevent), `spin` (a full circle of *same-direction* quarter-turns within 2s with under ~60px of net drift — the "tank visibly rotating in place" failure, which `jitter` is structurally blind to since a rotation cycle contains no A→B→A triple), `churn` (300px+ of path driven inside a 4s window that ends under ~60px from where it started — full-speed "dancing", the complement of `stall`, which needs near-zero speed, and of `spin`, which needs rotation), `clustering` (at least `CLUSTER_MIN_GROUP` enemies mutually within `CLUSTER_RADIUS` of each other, sustained for `CLUSTER_FRAMES_THRESHOLD` — enemies piling up instead of spreading out across the engagement-slot system in `simulation.rs::Game::update`), `wall-grind` (driving into static terrain: `touching_static` with a nonzero move command sustained 2s — the failure `stall` can't see, since a grinding tank may still be moving), `bump-rate` (rising edges of terrain contact per trailing minute above a measured cap — "hitting obstacles too much", literally; threshold measured from real sweeps, table in the const's comment), `low-progress` (commanded > half top speed while achieving < 30% of it for 3s — intent-vs-outcome, ~4× the AI's own `STUCK_ESCAPE_SECONDS` so it fires only when the escape hatch is failing repeatedly), `never-arrived` (a live enemy whose spawn-time A* route existed — `Game::nav_path_cells` — but who never entered `ENEMY_ATTACK_RANGE` of the player within a grace-plus-4×-ideal time budget; trace mode prints a per-enemy route/ideal/stretch table, and the verdict runs once at round end), and `invariant` (frame-level physics sanity — non-finite position/velocity, escaped the battlefield bounds, speed above a generous cap; the one kind that also covers the player and wrecks, since a solver blow-up isn't explained by the scripted `Scenario`. It also folds in `Event::PhysicsQuarantine`, rapier's own authoritative NaN report: that fires inside the step that produced the bad state and covers the wall/obstacle/frog bodies no tank snapshot shows, so it is reported world-level — `tank=WORLD`, no heatmap point — rather than against a slot). **Deliberate-hold suppression**: `stall`/`stale-start` are muted for a tank that's standing still *on purpose* — fired within the trailing few seconds, currently holds an aligned in-range firing solution, or is waiting out a retreat recharge (`TankTrack::deliberate_hold`, fed by ammo/fire tracking in the snapshots) — added when the nav-grid rasterization fix made correctly-stationary firing tanks the norm and every one of them false-positived against an AFK player. Add a new anomaly kind by extending `TankTrack` + `check_anomalies` the same way; tune thresholds as named consts at the top of `probe.rs`, not inline magic numbers.
    **Known blind spot**: `jitter`'s A→B→A pattern-match can't tell rapid, wasteful flip-flopping apart from legitimate multi-leg weaving through a dense/maze-like obstacle cluster (each leg held a genuine ~0.3-0.5s, not a frame-to-frame flicker, when checked frame-by-frame with `--log-every 1`) - a high `jitter` count is not on its own proof of a real problem the way `stall`/`border-stuck` are; corroborate with a per-frame trace or an actual playtest before treating it as a regression.
  - **`--rounds N` for statistical coverage.** A single round has one random spawn layout and one AI RNG roll, so a bug that only shows up 1-in-N rounds needs many rounds to catch reliably. `--rounds N` re-`init`s the game N times (same as the game's own restart path) and, once N>1, suppresses the per-frame trace/`--log-every` entirely — only `ANOMALY` lines plus a one-line-per-flagged-round summary and a final aggregate print. This is the default way to go looking for stale/stuck/jittering-tank bugs: `cargo run --bin probe -- --scenario afk --enemies 4 --frames 900 --rounds 30` sweeps 30 independent rounds in about a second of wall-clock time (headless, no real-time wait) and reports only what's actually wrong. The harness's first major scalp: sweeps surfaced enemies stalling/spinning shortly into rounds, which was eventually root-caused (via the map linter's failure dumps + probe traces) to `Grid::build`'s old any-overlap rasterization stacking a hidden extra half-cell of margin — sealing much of the map into pockets whose unreachable waypoints made `Ai::wander` re-roll every frame. Fixed by the cell-center occupancy rule in `Grid::build` (plus `Ai::wander_pocketed`); sweep spin/churn counts dropped several-fold across scenarios.
  - **Sweep ergonomics** (Phase 6 of docs/gameplay-verification-design.md): `--json-out <file>` writes one JSON Lines record per round as it finishes (seed, map, all twelve anomaly counts, per-tank route/stretch/contact/distance stats — `path_cells: null` marks the no-route-at-spawn population); `--budget <kind>=<max>` (repeatable; kinds are the twelve ANOMALY tags plus `total`) exits 1 on any breach, 0 otherwise; `--heatmap` prints per-kind ASCII grids of anomaly positions at `PATHFIND_CELL_SIZE` granularity — its first render localized the default map's stalls to the walled top strip the linter had flagged. `just probe-sweep` is the standing default-map health check; `just probe-fixtures` (mirrored in `.github/workflows/ci.yml` alongside `cargo test --lib`) sweeps every fixture at a pinned seed against exact recorded ceilings — deterministic, so an exceedance is a real behavior change; the recipe's comment carries the re-baselining policy, and the definitive standing baselines live in the design doc's wave-5 close-out.

- **`src/maplint.rs` — static battlefield-map linter** (Phase 3 of docs/gameplay-verification-design.md; run `cargo test --lib maplint`). Exhaustive, provable checks over a map's finished static terrain, set up as a real seeded headless `Game::init` and read through the exact `Game::nav_grid` the AI steers by (occupancy queried via `blocked_ahead`/`boxed_in`, so the linter *cannot* disagree with what the AI sees). Level checks on top (docs/maps-to-levels.md): `gate-not-on-edge`/`gate-blocked`/`waves-no-gates` (errors), `enemy-frog-unreachable` (error), `hunt-missing-enemy-frog` (warning: the game falls back to a band spot); the spawn-band capacity check runs only for the Band plan; `maps/missions/` fixtures assert a clean profile. Five terrain checks: playfield connectivity/reachability (frog + every pickup slot within approach reach; a pickup approachable only once destructible non-Iron walls are shot away is a `gated-pickup` *warning*, computed from a second flood fill over an Iron-only grid - Iron is the one permanent material), open-but-boxed-in cells, spawn-band capacity (the same legality predicate `Game::init`'s enemy sampler uses, counted per nav-cell center), planner-vs-physics agreement (grid-open cells a worst-case tank AABB physically can't occupy — the stuck-tank generator class), and single-cell-wide corridors. The gate `supported_maps_no_new_errors` permits only each supported map's recorded debt in `KNOWN_ERROR_KINDS` (error *kinds*, not counts — default.toml is a live editing canvas) and fails instantly on any new error class; `maps/test/` fixtures assert their intended lint profiles; every other `maps/*.toml` is lint-and-print only (`--nocapture` to see it). default.toml currently carries no lint errors: 28 of its pickup slots (the top-edge strip and the bottom-right rows) are `gated-pickup` warnings - not AI-reachable on intact terrain, but reachable once brick is shot away (the three health packs at the top center sit behind a permanent iron gate, breachable only through the brick columns beside it). (Its border band used to have zero legal spawn cells under an older, distance-based predicate; the shared `enemy_spawn_legal` predicate now counts ~40 there, so `spawn-band-too-tight` is no longer part of that map's debt.) **Two players:** `check_players` adds `no-start` (warning), `player2-unreachable` (error: player 2's spawn is outside player 1's playfield) and `players-too-close` (warning: a `start2` inside the clearance `Game::init` keeps, so it is ignored); the spawn-band and wave-gate checks avoid both players. The test harness lints every map twice (single, then two-player for the player-2 kinds only), so `supported_maps_no_new_errors` covers the fallback placement.

## Web / wasm build
The game also compiles to `wasm32-unknown-emscripten` and runs in the browser via `sola-raylib`'s `game_loop::run` (`main.rs`), which uses `emscripten_set_main_loop_arg` on web instead of the blocking `while` loop used on native. Full background: `../sola-raylib/book/src/web.md`.
- **`game_loop::run`'s `fps` argument means something different on each side, and web wants `0`.** On native it is `SetTargetFPS`, a cap. On web it picks the loop's *driver*: emscripten reads any `fps > 0` as a request for `EM_TIMING_SETTIMEOUT` at `1000/fps` ms and only `0` selects `EM_TIMING_RAF` (`libeventloop.js`, `setMainLoop`). A timer is not synced to the display refresh, so a finished frame waits an arbitrary slice of a refresh interval before it is shown - felt as lag between a key and the tank answering it - the phase drifts into judder, and browsers throttle timers harder than rAF, phones most of all. `main.rs` therefore passes `0` under `cfg!(target_os = "emscripten")` and 120 on native. Halving the web loop rate is safe because physics runs on its own `PHYSICS_FIXED_DT` accumulator and everything else scales with `f.dt`.

- One-time setup: `just setup-web` — installs emsdk (pinned to 5.0.6 in `tools/setup_emscripten.sh`; newer versions have a wasm-opt bug, see the script) and the Astro site's JS dependencies (`cd site && yarn install`). The `wasm32-unknown-emscripten` rustup target and node/yarn themselves come from `devenv.nix`'s `languages.rust.targets`/`languages.javascript`, so a `direnv reload`/new shell after pulling `devenv.nix` changes is enough to get them.
- Build + run: `just build-web` then `just serve-web` (http://localhost:4321). `just build-web-dev`/`just serve-web-dev` do the same with `--features dev-tools` (note `serve-web` *depends on* `build-web`, so running it after a `build-web-dev` silently rebuilds without the feature and the panel vanishes - use `serve-web-dev`, or `just preview-web` to serve `site/dist/` as-is): the wasm exports the tuning C API and the page's **Tuning** panel appears under the canvas (docs/runtime-tuning-design.md). The panel is rendered entirely from the schema the wasm exports (`site/src/pages/index.astro`'s inline script), so a new `tunables!` row needs no site change; it shows itself only when `Module._bb_tuning_schema_json` exists, so a production wasm never has it. Edits persist in `localStorage` and are re-applied on reload; "Copy JSON" gives a `--tuning` file, "Copy as Rust" gives table rows to paste back into `tuning.rs`.
- **The site that ships the game is an Astro project at `site/`** (`site/README.md` has the full picture). Astro owns the page shell (`site/src/pages/index.astro` — port of the old hand-rolled `web/shell.html`, now deleted), styling, and any marketing content; it never builds or touches the game itself. `just build-web` does the Rust build first (`cargo build --release --target wasm32-unknown-emscripten`), copies `bongbong.{wasm,js,data}` into `site/public/game/` (gitignored — a build artifact, not source), then runs `yarn build` inside `site/` to produce `site/dist/`. That ordering matters: Astro's `public/` directory is copied byte-for-byte into `dist/` with no processing, which is required since Emscripten's glue JS looks up `bongbong.data` by a fixed relative path next to itself — hashed/bundled asset names would break it. Minification of the wasm/JS glue happens entirely on the Rust/Emscripten side (Cargo's release profile forwards `-O3` to `emcc`, which runs Binaryen's `wasm-opt` and Emscripten's own JS minifier) before Astro ever sees the files; Astro/Vite's own minification only covers its own build output (the page markup/CSS/scripts it actually processes). `wrangler.toml` deploys `site/dist/`, not `target/web/` (that staging directory no longer exists).
- `.cargo/config.toml` carries the emscripten linker flags (GLFW3, memory growth, `--preload-file static@/static` so `static/tanks.png`-style paths resolve unchanged) and an `[env]` block pinning `CC_wasm32_unknown_emscripten`/`CXX_wasm32_unknown_emscripten`/`AR_wasm32_unknown_emscripten` to the real `emcc`/`em++`/`emar` — **required under devenv/nix**, because nix's C toolchain module sets a global `CC` pointing at a host-wrapped clang that injects flags (e.g. `-fzero-call-used-regs`) `emcc` rejects for the wasm target; cc-rs picks the global `CC` over emcmake's own toolchain unless the target-specific env var wins. This bit isn't in sola-raylib's book (written for a non-nix host) — it's specific to this project's devenv setup.
- **The canvas box must keep the render target's own shape (1280x752: the field plus the HUD bar, `aspect-ratio: 1280 / 752`), and full screen is two mechanisms.** raylib maps a touch by dividing by the canvas's CSS *box* (`emscripten_get_element_css_size`, see `rcore_web.c`'s `EmscriptenTouchCallback`), so the box has to be the same shape as the bitmap. The page used to size width and height independently and lean on `object-fit: contain`, which *does* letterbox a canvas - verified in a browser - putting the picture in a band inside the box while taps were still measured against the whole box: on a phone every tap landed in the wrong place vertically. `site/src/pages/index.astro` now sizes the box from one `--canvas-w` custom property with `aspect-ratio: 1280 / 752`, which the overlay controls also align to. The canvas carries `touch-action: none` because the builder paints by dragging and cannot let the browser claim drags for scrolling or pinch-zoom. Full screen has **three** outcomes, not two: `requestFullscreen` where it exists (desktop, Android, iPadOS) gives real full screen; the `.immersive` class takes the whole viewport but **cannot hide Safari's URL bar on iPhone** - no page can, it is a platform restriction - and Add to Home Screen is the only chrome-free window there, which is why `apple-mobile-web-app-capable` is set. That last route is deliberately *not* advertised on the page: an on-canvas note explaining a platform limitation the player cannot act on mid-round is a wall of text over the game. Two traps in the toggle: the modern API's rejection is *async*, so the label is refreshed from inside the promise handlers rather than after the call; and old WebKit's prefixed `webkitRequestFullscreen` returns `undefined` rather than a promise, so calling `.then` on it throws and aborts the handler, leaving neither real full screen nor the fallback.
- **Both Shift keys reach the game only through a page shim.** Emscripten's GLFW layer (`emsdk/upstream/emscripten/src/lib/libglfw.js`) maps the DOM Shift key (`keyCode 0x10`) to `GLFW_KEY_LEFT_SHIFT` whichever side was pressed - the right-shift case is commented out and `event.location`/`event.code` are never read - so raylib never reports `KEY_RIGHT_SHIFT` on the web and player 1 could not fire in two-player mode. `site/src/pages/index.astro` keeps `window.bbShift` (bit 1 ShiftLeft, bit 2 ShiftRight, from `keydown`/`keyup` on `event.code`, cleared on blur) and `main.rs`'s `shift_state` reads it once a frame through `emscripten_run_script_int`; native reads raylib's two keys.
- **Shaders need a GLSL ES 100 port for web.** raylib's `PLATFORM_WEB` build defaults to OpenGL ES2 (`raylib/cmake/LibraryConfigurations.cmake`), which only accepts GLSL ES 100, not desktop's `#version 330`. `static/web/{shockwave,muzzle_flash,impact}.fs` are hand-ported copies of `static/*.fs` — same logic, only syntax changes (`#version 100` + `precision mediump float;`, `in`/`out` → `varying`, `texture()` → `texture2D()`, `finalColor =` → `gl_FragColor =`). `main.rs`'s `shader_path()` picks the right directory via `cfg!(target_os = "emscripten")`. If a shader effect's logic changes, port both files by hand — there's no shared source.
- No audio yet, so the build skips `-sASYNCIFY=1`. The moment `InitAudioDevice`/sound is added, both `-sASYNCIFY=1` needs to go back into `.cargo/config.toml` rustflags (raylib's audio backend needs it) — `game_loop::run` alone won't cover it.
- **CI deploys, two lanes sharing one build:** `.github/actions/build-web/action.yml` is a composite action holding the CI web-build steps (the CI mirror of `just build-web`; the Rust/emsdk version pins live there as input defaults — keep in sync with `devenv.nix`/`tools/setup_emscripten.sh`). `.github/workflows/cloudflare-deploy.yml` uses it on version tags to `wrangler deploy` production (the `bongbong` Worker serving bongbong.io, static assets per `wrangler.toml`). `.github/workflows/pr-preview.yml` uses it on every PR (passing `cargo-features: --features dev-tools`, so **PR previews are the QA surface with the tuning panel; production never gets it**) to deploy an **ephemeral per-PR preview Worker** (`bongbong-pr-<N>`, played at **`pr-<N>.preview.bongbong.io`** — a Workers Custom Domain attached via a CI-generated `wrangler.preview.toml` (gitignored; `compatibility_date` is grep-read from `wrangler.toml`), since `custom_domain` routes can't be expressed as CLI flags; Cloudflare auto-creates the DNS record + per-hostname cert (pr-N.preview.\* sits below the universal `*.bongbong.io` cert, so first TLS can lag a minute — `workers_dev = true` keeps a workers.dev fallback URL, subdomain `otobrglez.workers.dev`), and never touches bongbong.io's own routes), posts/updates a sticky PR comment with the URL, and on PR close deletes the worker (`wrangler delete --name …` — removes the custom domain/DNS with it; a never-deployed worker is tolerated as already-clean). Both lanes reuse the same two repo secrets (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`); the custom-domain attach needs zone-scoped Workers Routes:Edit on top of account-level Workers Scripts:Edit — the live account token ("bongbong-token") already carries both (incl. a "Workers Routes Write on all zones" policy; verified in the dashboard 2026-08-27), and DNS/certs for custom domains are Cloudflare-managed so no DNS:Edit/SSL:Edit is required. Fork PRs get no secrets under `pull_request`, so previews are same-repo-branch only by design — never "fix" that with `pull_request_target`.

## Releases (cargo-dist)
Native binary releases (macOS x86_64/aarch64, Linux x86_64, Windows x86_64 — deliberately *not* the wasm/web build, which stays on its own `just build-web`/`serve-web` path above) are built and published to GitHub Releases by `.github/workflows/release.yml`, generated by [cargo-dist](https://opensource.axo.dev/cargo-dist/) (`dist-workspace.toml`; `[profile.dist]` in `Cargo.toml`). Triggered by pushing a tag matching `v{X}.{Y}.{Z}` — bump `Cargo.toml`'s `version`, tag it to match (`git tag v0.0.8 && git push --tags`), CI does the rest.
- **`static/` ships bundled in every release archive**, not embedded in the binary. `main.rs` loads textures/shaders by path relative to the process's *working directory* (`"static/scifi_tanks_sheet.png"` etc.), not the executable's location, so a downloaded release only works run from the folder it was extracted to. `dist-workspace.toml`'s `include = ["static"]` handles the bundling; if this ever needs to work from an arbitrary CWD (e.g. a PATH install), the fix is resolving asset paths against `std::env::current_exe()` instead — not done, since no installer needs it yet (see below).
- **No installer scripts** (`installers = []`) — this is a windowed game people download and run, not a CLI tool anyone wants on `$PATH`, so releases are plain per-platform archives only (no `curl | sh`/PowerShell/homebrew).
- **Which binaries an archive holds is the per-target `[dist.binaries]` table in `dist-workspace.toml`** (`bongbong` and `probe` on every target). It must list every target and exclude any `required-features` bin (`bbmcp`): dist builds the package with no features, then fails with `failed to find bin bbmcp` if such a bin is expected. `probe` ships deliberately - a small headless debug tool with no sensitive content; drop it from the lists if that ever changes. A `[dist.binaries]` table opens a TOML subtable, so keep it *after* the last `[dist]` scalar (`msvc-crt-static`) and before `[dist.dependencies.apt]`.
- **Linux needs raylib's system dev packages** (`[dist.dependencies.apt]` in `dist-workspace.toml`) — X11/OpenGL/audio/input headers, since raylib-sys builds from source. Same package list as `../sola-raylib`'s own working CI (`../sola-raylib/.github/workflows/ci.yml`), not assembled from general advice. macOS/Windows runners need nothing extra.
- **No `LICENSE` file yet** (left out deliberately for now) — cargo-dist works fine without one, but revisit before any installer type that surfaces it (homebrew formula, etc.) gets added.
- `dist generate --mode ci` regenerates the workflow after editing `dist-workspace.toml`. One local gotcha: **`--allow-dirty` silently no-ops the actual file write** in this cargo-dist version (0.32.0) — `dist plan`/`dist generate` report success either way, but only the run *without* `--allow-dirty` actually writes `.github/workflows/release.yml`. Also make sure `.github/workflows/` exists first (`mkdir -p`) — `dist generate` doesn't create the directory itself.
